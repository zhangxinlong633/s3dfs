# 部署

s3dfs 按三种角色部署。API 不保存对象正文，前面可以放多台，用负载均衡把客户端接上来。索引和 block 是有状态的，不能当成无状态进程随便换盘。

## 什么叫高可用

同时满足下面几条，才把这套部署当成高可用：

- 索引至少 3 个地址，按 dleveldb 自己的文档组成集群。`S3DFS_INDEX_URLS` 用逗号列出。当前地址失败时，控制面会改写下一条；新节点不会在这个仓库里自动拿到历史 key。
- block 台数不少于 `S3DFS_DATA_REPLICAS`（默认 3），并且用 `@zone` 把它们分到不同机架或可用区：`b1=10.0.0.1:9100@rack-a,b2=10.0.0.2:9100@rack-b,b3=10.0.0.3:9100@rack-c`。
- 写入默认达到多数就成功。3 副本要 2 份 block 成功，然后才写索引。没写上的那一份由后台修复补。要用更严的条件，设置 `S3DFS_WRITE_QUORUM`。
- 至少两台 API，前面用负载均衡。任一 API 退出，客户端重试另一台。

只有一台 block 时，有效副本和法定人数都是 1。这种布局可以开发，不能叫高可用。

## 入口

API 默认听 `:9000`。两个变量都设置时才校验 SigV4：

```bash
S3DFS_ACCESS_KEY=...
S3DFS_SECRET_KEY=...
```

没配密钥时，任何能连上端口的客户端都能读写。公网入口必须配密钥。TLS 在反向代理上终止，API 进程本身不提供证书。

每个响应带 `x-amz-request-id`。进程往标准输出打一行 JSON，里面有这个 id、方法、路径、状态码和耗时。`GET /_s3dfs/health` 在索引不可达时返回 503。`GET /_s3dfs/metrics` 返回自进程启动以来的状态码计数，不经过控制台。

C 网关使用同一对密钥和同一套法定人数、故障域规则。它认 `x-amz-date`，不认只有 `Date` 的请求。

## 单机

一条索引、一台 block、一台 API 就能跑。把 `S3DFS_DATA_REPLICAS` 设为 1，避免把开发布局误当成 3 副本。数据目录、端口和启动命令以仓库 README 为准。
