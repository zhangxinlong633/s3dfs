# 删除空洞与 compact（虚拟记录 ID）

这套方案**已经落地**。索引 locator 只记稳定的 `recId`；删除会立刻追加墓碑、去掉 dleveldb 里的定位，并出一张清理票；空闲或手动 compact 再把还活着的记录写到新的 `.blk` 文件，回收空洞，不必改索引。

这份文档说明为什么不把文件 offset 长期写在索引里，以及怎样用「虚拟记录 ID + 本地映射表」回收空洞，同时尽量不影响现有读写热路径。

## 要解决的问题

block 文件是追加写的。删除或覆盖之后，旧记录还留在文件中间，形成空洞。要收回这些空间，只能把还活着的记录写到新文件（或新的一段），然后丢掉旧文件。

如果索引里直接记 `(blockId, offset, recLen)`，重写之后这些数字都会变。那就必须在 compact 时回写 dleveldb：对象一多，索引会被集中更新；compact 过程中如果有新的 Put / Delete，还可能把新 locator 覆盖掉。前面讨论过「先写新文件、按旧位置比对再回写、成功后再删旧文件」，这条路能做对，但 compact 和索引耦得太紧，失败模式也多。

## 核心想法：索引只记虚拟 ID

索引不再指向文件里的物理偏移，只记一个在该 block 节点上稳定的**虚拟记录 ID**（`recId`）。文件里的真实位置，只留在这块节点自己的一张表里：

```
dleveldb locator        block 节点本地表              .blk 文件
(nodeId, recId)   -->   recId → (blockId, offset, recLen)  -->  TLV 记录
```

`recId` 是该节点上单调递增的 64 位整数，可以用十六进制表示（例如 `aabb`、`aacc`）。它只需要在这一台 block 上唯一；集群范围内靠 `(nodeId, recId)` 区分。对象被覆盖时发一个新的 `recId`，索引改指向新 ID；被删除的旧 ID 从映射表里拿掉（或等清理时拿掉）。文件被重写之后，例如 `aabb` 已经没有了，`aacc` 还在，索引里仍然是原来的 `aacc`，不必改。

这张表**不是**再引入一个本地 LevelDB 作为第二份真相。`recId` 会作为 TLV tag 写进记录本身。节点启动时扫描 `.blk` 即可重建映射；表丢了也可以扫回来。和现在「索引丢了可以扫文件重建」是同一条原则，只是多了一层「物理位置只在节点内部解释」。

跨块大对象的 prev 链也改成指向前一段的 `recId`，不要再记前一段的文件 offset。这样 compact 重写段数据时，链条本身不用改，索引里仍然只存最后一段的 `recId`。

## 删除与清理怎么拆开

对用户可见的删除必须是实时的，但不必在删除的当时重写整个 block 文件。

1. **实时路径（出票）**：Delete 仍然先在各副本的 block 上追加墓碑，再删掉 dleveldb 里的 locator。对象立刻不可读、重建索引也不会把它救回来。与此同时，对应 block 节点记一张待清理的票（至少包括相关 `recId` 或所在文件、大约能收回的字节）。出票只要追加或增加计数，不重写 `.blk`。
2. **空闲路径（定时清理）**：block 节点在比较空闲的时候，或按可配置的周期 / 空洞比例阈值，取出待清理的票，只处理值得合并的文件。扫描 TLV，保留还活着的记录（同一 key 以最后一条为准，最后一条是墓碑则丢弃），写到新的 `.blk`，**保留原来的 `recId`**，原子更新本地映射表，再删除旧文件。这一步不写 dleveldb。
3. 管理接口上的 compact 仍可手动触发，走同一套清理逻辑，便于运维，而不是删除热路径上的同步合并。

清理过程中旧文件先留着。映射表切换到新位置之后，持有旧物理偏移的读才会失败；对外 Get 每次都按 `recId` 查表，所以对客户端是透明的。若清理过程中有新的 Put / Delete，新记录追加到当前正在写的文件并分配新 `recId`，不会进正在被替换的旧文件，也就不会和这次合并互相覆盖。v1 实现里，compact 会持有该节点引擎的互斥锁，大文件合并时这个节点上的读写可能短暂停顿。

## 性能上为什么可行

当前走集群路径的 1 KiB 读取大约是 8,869 ops/s，p50 约 109 µs；不经索引、直接打到 block 大约是 19,361 ops/s，p50 约 50 µs（2026-11-17 00:40 Asia/Shanghai，同一套 `pnpm bench`）。这部分时间主要花在 HTTP 和索引上，其次才是一次 `pread`。Get 时多一次「`recId` → 物理偏移」的内存哈希查找，通常远小于 1 µs，相对这两条路径都不是同量级的开销。写路径只是多写一个 TLV tag、往内存表里插一项，仍然走现在的 group commit，不必多一次 `fsync`。

需要单独看的有三处：

- **内存**：每条活着的记录在映射表里大约几十个字节（`recId`、文件编号、偏移、长度）。一百万条活记录大致是几十 MB 量级，对 block 节点来说通常可接受。节点重启要扫一遍 `.blk` 才能恢复这张表，启动时间跟已有数据量有关，不在每次 Get 的路径上。
- **记录开销**：多一个 `recId` tag（类型、长度和 8 字节值，一共 14 字节）。这次实测里，5,000 个不压缩的 1 KiB 对象盘上从 5,463,890 字节变成 5,533,890 字节，盘上比约为 0.93x（上一轮 TLV、尚无 `recId` 时约为 0.94x）。16 KiB 以上对象里，这个比例可以忽略。
- **删除热路径**：仍然是墓碑 + 删索引 + 出票，不在删除时合并文件。删除延迟应与现在同一量级，这是把清理拆到空闲任务的主要原因。
- **compact 本身**：主要消耗磁盘读写，而且不再对每个存活对象回写 dleveldb。相比「重写文件后再批量改索引」，这是这套方案在性能上最明显的好处：清理 100 万个还活着的对象，不必对索引集群打 100 万次 locator 更新。这次官方 `pnpm bench` 为避免后台清理掺进数字，设置了 `S3DFS_COMPACT_INTERVAL_MS=0`，因此没有单独给出 compact 吞吐和回收比例。

综合来看，热路径（Put / Get / Delete 对用户可见的部分）适合采用虚拟 ID。与 2026-11-16 12:33 那次尚未使用 `recId` 的 TLV 基线相比，1 KiB 集群读写的 ops/s 与 p50 仍在同一水平（差异多在 2% 以内），看不出查找表带来的回退。代价主要是节点内存、每条记录多 14 字节，以及启动扫描。空间回收放到空闲清理里，避免把合并的磁盘开销打进删除请求。

## 不采用的做法

- **重写文件后回写 dleveldb**：可行，但 compact 必须和索引事务绑在一起，要用旧位置做比对，以免覆盖新写入。对象多时索引更新量大，部分失败还要重试。不作为首选。
- **清理时暂停该节点写入**：实现简单，但伤害在线写入，只适合维护窗口，不适合作为常规删除回收。v1 实现里互斥锁仍可能让大 compact 短暂挡住该节点的读写，这是实现限制，不是把「停写」当成常规方案。
- **在旧文件里原地重用空洞**：TLV 可以标出已删除记录，但空洞大小不一，容易碎片化，分配和并发读更复杂。暂不做。

## locator 与 TLV（已按此实现）

索引 locator 已升到 `v: 3`。对外仍保留未压缩的 `size` / `crc`、`storedSize`、`compressType`、副本和节点信息；定位字段由 `blockId` / `offset` / `recLen` 改为 `recId`。block 的 HTTP 读取按 `recId` 查表，而不是携带文件偏移。

TLV 增加 `recId` tag（`S3DFS_TAG_REC_ID`，`0x000E`，8 字节）；跨段的 prev 改为前一段的 `recId`。打开存储时扫描 `.blk` 重建映射，`next_rec_id` 为已见最大值加一。本仓库目前没有需要兼容的生产数据。

后台清理由 `S3DFS_COMPACT_INTERVAL_MS`（默认 30000，设为 0 则关闭定时任务）和 `S3DFS_COMPACT_DEAD_RATIO`（默认 0.2，即 `deadBytes / bytesOnDisk` 达到该比例才自动合并）控制。手动可通过 `POST /_s3dfs/block/compact` 或控制面的 `compact()` 触发，走同一套逻辑。测试里会关掉后台任务，再显式调用 compact。

## 已经做的和先不做的

已经做：`recId` 与内存映射表（可由 TLV 重建）、Delete 实时出票、空闲 / 定时 / 手动触发的文件合并、大对象链条改为 `recId`、文档与测试（删除后空间下降、同一个 `recId` 在 compact 和重新打开后仍能读到、其它未删除对象不受影响）。

先不做：用本地 LevelDB 持久化映射表；原地空洞分配；自动在副本之间修复或迁移数据；把清理做成跨节点的分布式事务。这些不影响本方案是否成立。
