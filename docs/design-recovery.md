# 故障与恢复

| | |
| --- | --- |
| 读者 | 评估能否把这套集群当作业务数据存放处的人 |
| 本文回答 | 哪一类故障下读写还能继续，哪一类不能，以及已经落地的补齐手段 |
| 相关 | [部署](deploy.md)、[上线标准](diff/production.md)、[索引与 block](design-replication.md) |

没有「掉点后几秒一定恢复」的测量，也没有架构上的恢复时间上限。已经落地的是：探测并避开故障 block、本次请求改走剩余副本、活副本不足时后台补齐。这不是把集群持续收敛成「副本数永远是 3」的控制器。

状态并没有消失。数据位置在 dleveldb 里，正文在各 block 的 `.blk` 里，block 进程还要在内存里维持 `recId` 映射。S3 API 相对弱状态，本身更接近可替换的客户端；需要持久化的部分在索引和 block 上。说明见 [索引与 block 集群](design-replication.md) 和 [删除空洞与 compact](design-compaction.md)。

## 已经有的

- 对象正文默认 3 副本（有效值是 `min(配置值, 当前存活的 block 节点数)`），索引里记成 `bucket/key`、`bucket/key:1`、`bucket/key:2`
- API 按 `S3DFS_HEALTH_INTERVAL_MS`（默认 5 秒）对 block 做健康检查，把 up / down 记下来
- Get 会跳过已标记为 down 的节点，并在本次请求里依次尝试剩余副本；某一副本连不上或校验失败时，改试下一份，不必先等健康检查周期走完
- 新的 Put 只在探测为存活（或尚未探测过）的节点里挑选。节点被标为 down 之后，新写入不会再选它
- Head 在副本机器暂时不可达时，可以用索引里记下的 size / crc / mtime
- 索引读可以走 dleveldb 剩余的 KV 副本
- S3 API 可以起多份，都指向同一组索引和 block；API 进程本身不打开本地 store
- 故障的 block 节点如果带着原来的磁盘回来，只要对象还在，原数据位置可以继续用。数据目录根上有 `s3dfs-layout.json`，修复程序按它扫 `blocks/*.blk` 和索引键，不必打开源码。进程启动时优先读本地 `recmap.s3m`，再补扫快照之后的新数据，快照不可用才扫描全部 `.blk`。时间跟数据量有关，不能保证是秒级
- 索引里的定位信息若丢了，可以对各 block 扫描 `.blk` 重建数据位置（删除有墓碑，避免把已删对象救回来）。这是修复索引的手段，不是秒级切换

## 什么情况下请求还能继续

这些情况的含义是：**不必等故障节点恢复就能继续读写已经存在的对象，或把新对象写到还活着的节点**。它们不是已经测过的秒级 SLA。

| 情况 | 能否继续 | 说明 |
| --- | --- | --- |
| 一台 block 宕机，该对象在别的 block 上还有副本 | Get 通常可以继续 | 本次请求会改试剩余副本。把该节点从新的 Put 里拿掉，最多要等到下一轮健康检查（默认 5 秒） |
| 一台 block 宕机，只影响新对象的放置 | 新 Put 可以写到还活着的节点 | 后台或 `POST /_s3dfs/repair` 会在还有空闲节点时把份数补回去，并去掉 down 的数据位置 |
| 一台 S3 API 进程退出，还有别的 API，或可以很快拉起同一份 API | 客户端重试后可以继续 | API 不保存对象正文，索引和 block 还在即可。仓库没有内置负载均衡或自动拉起 |
| 索引某一节点不可达，其余副本仍达到写法定人数 | Get / Put 往往还能继续 | 读走剩余 KV 副本。主节点不可达时，偏好列表里第一个存活节点在达到法定人数后接受写入 |
| 故障 block 带着原盘回来 | 原数据位置可继续用 | 启动时优先读 `recmap.s3m` 并补扫尾巴；快照不可用才全量扫描。时间跟数据量有关，不能保证是秒级 |

## 什么情况下不行

| 情况 | 结果 |
| --- | --- |
| 有效副本是 1（只有一台 block，或当时只写了一份），而这一份所在的节点丢了 | 这些对象读不出来，也不会自动出现在别的机器上 |
| 某个对象的全部数据副本都丢了 | 该对象不可读，没有修复流程把它补回来 |
| 索引剩余副本达不到写法定人数 | Put / Delete 失败。不允许两个分区同时持有多数 |
| 新的索引节点刚加入、历史 key 尚未追平 | 不能立刻把全部读流量指到这台空节点。加入环之后，dleveldb 按较新的 mtime 把本机负责的 key 补齐 |
| block 进程重启 | 优先读本地快照并补扫新数据，快照不可用则仍要全量扫描。这能缩短常见重启，但不是无状态的秒级替换，也没有测过确定上限 |
| 节点或磁盘彻底丢失 | 还有活副本、并且还有空闲节点时，修复会再写一份并退役失效数据位置。一份都不活则记为 `lost`，补不回来 |
| FUSE 尚未 `close` 的写入 | 只在客户端临时文件里，集群里还没有这个对象；挂载进程或 API 在关闭前退出，这部分内容不会进 block |
| 「任何情况下秒级恢复」或「一秒都不能停」的数据库负载 | 不是当前目标，也没有这样的测试或保证 |

## 用得省心

对业务侧，已经可以依赖的是：坏掉的 block 会退出新写入，读会改走剩余副本，活副本不足时后台补份。索引在剩余副本达到法定人数时继续接受写入，节点回来后按较新的 mtime 追平。一个对象已经没有任何活副本时，记为 `lost`，健康检查返回 503，数据补不回来。

还没有做成的是 API 流式上传，避免整个对象进内存。能不能把某一套集群当作唯一副本，以 [上线标准](diff/production.md) 里的演练记录为准，不以本文的功能清单为准。

## 第一期：对象副本补齐

已经做的是一次对账。API 会扫描可见的对象 key，比较「活着的数据副本数」和 `min(配置副本数, 当前存活的 block 节点数)`。不够就从一份还活着的副本读出内容，再写到还没有这份对象的存活节点。已经 down 的数据位置会删掉并重新编号。一份都不活就记为 `lost`。自本次 API 进程启动以来的 `lost` 会累加，`GET /_s3dfs/health` 因此返回 503，直到进程重启且之后的修复不再记到丢失。

- 手动触发：`POST /_s3dfs/repair`
- 后台周期：`S3DFS_REPAIR_INTERVAL_MS`，默认 30 秒；设为 0 则只保留手动触发。同一周期也会按桶上的生命周期删过期对象
- 加机器、有效副本从 1 或 2 变成 3 时，已有对象也可以被补齐
- 某一副本所在节点宕机、但别处还有活副本、并且还有空闲的存活节点时，会再写一份

现在明确还没有的：

- 没有活副本的对象（单副本丢掉，或全部数据节点都丢了）补不回来
- 补齐仍走现有的整对象 Get / Put，大对象会进 API 内存
- 索引在主节点不可达时的写入和回来后的追平由 dleveldb 完成，不在这次对象副本对账里
- 控制台目前没有补齐按钮，只走管理接口或后台任务

## 还没有做的

- dleveldb 节点加入后的范围迁移 / catch-up repair
- dleveldb primary 不可达时的安全写故障转移
- block 重启在快照不可用时仍可能全量扫盘；启动时间没有测过，不能写成秒级指标
- 针对掉点、切主、重启的恢复时间测试，因此文档里不写具体的秒数指标

有活副本时，现在不但能躲开坏点，还可以在还有空闲节点时把份数补回去。索引写故障转移如果缺着，只把副本补齐做完，仍然不能单独做到连续可用。

## 和设计方向的关系

要把「故障当作常态、尽量自己恢复」做成，需要把两件事分开：服务进程能否被替换，以及状态下沉的那一层是否自己扛得住。API 已经比较接近可替换；索引和 block 仍是有状态的。状态下沉到 dleveldb 和 `.blk` 之后，可靠性底线就在这两层：副本补齐是 block 这一侧的对账；索引切主和追赶还缺着。只把 API 做快，并不能单独做到连续可用。
