# 故障与恢复

先说结论：**不是任何情况下都能秒级恢复**，也没有测过「掉点后几秒一定恢复」这种数字，更没有一个架构上确定的恢复时间上限。现在有的是探测和避让：有剩余副本时，请求可以改走别的节点，不必等故障节点回来。缺的副本不会自动补上，系统也不会像 Kubernetes 那样持续把实际状态修回「副本数应该是 3」。

状态并没有消失。locator 在 dleveldb 里，正文在各 block 的 `.blk` 里，block 进程还要在内存里维持 `recId` 映射。S3 API 相对弱状态，本身更接近可替换的客户端；需要持久化的部分在索引和 block 上。说明见 [索引与 block 集群](design-replication.md) 和 [删除空洞与 compact](design-compaction.md)。

## 已经有的

- 对象正文默认 3 副本（有效值是 `min(配置值, 当前存活的 block 节点数)`），索引里记成 `bucket/key`、`bucket/key:1`、`bucket/key:2`
- API 按 `S3DFS_HEALTH_INTERVAL_MS`（默认 5 秒）对 block 做健康检查，把 up / down 记下来
- Get 会跳过已标记为 down 的节点，并在本次请求里依次尝试剩余副本；某一副本连不上或校验失败时，改试下一份，不必先等健康检查周期走完
- 新的 Put 只在探测为存活（或尚未探测过）的节点里挑选。节点被标为 down 之后，新写入不会再选它
- Head 在副本机器暂时不可达时，可以用索引里记下的 size / crc / mtime
- 索引读可以走 dleveldb 剩余的 KV 副本
- S3 API 可以起多份，都指向同一组索引和 block；API 进程本身不打开本地 store
- 故障的 block 节点如果带着原来的磁盘回来，只要对象还在，原 locator 可以继续用；进程启动时优先读本地 `recmap.s3m`，再补扫快照之后的新数据，快照不可用才扫描全部 `.blk`。时间跟数据量有关，不能保证是秒级
- 索引里的定位信息若丢了，可以对各 block 扫描 `.blk` 重建 locator（删除有墓碑，避免把已删对象救回来）。这是修复索引的手段，不是秒级切换

## 什么情况下请求还能继续

这些情况的含义是：**不必等故障节点恢复就能继续读写已经存在的对象，或把新对象写到还活着的节点**。它们不是已经测过的秒级 SLA。

| 情况 | 能否继续 | 说明 |
| --- | --- | --- |
| 一台 block 宕机，该对象在别的 block 上还有副本 | Get 通常可以继续 | 本次请求会改试剩余副本。把该节点从新的 Put 里拿掉，最多要等到下一轮健康检查（默认 5 秒） |
| 一台 block 宕机，只影响新对象的放置 | 新 Put 可以写到还活着的节点 | 有效副本数会下降，不会在别的机器上自动补回丢掉的那一份 |
| 一台 S3 API 进程退出，还有别的 API，或可以很快拉起同一份 API | 客户端重试后可以继续 | API 不保存对象正文，索引和 block 还在即可。仓库没有内置负载均衡或自动拉起 |
| 索引某一副本不可达，但还能读到 locator | Get / Head / List 往往还能继续 | 读走剩余 KV 副本。写索引是否成功，取决于 dleveldb 的主节点是否可达 |
| 故障 block 带着原盘回来 | 原 locator 可继续用 | 启动时优先读 `recmap.s3m` 并补扫尾巴；快照不可用才全量扫描。时间跟数据量有关，不能保证是秒级 |

## 什么情况下不行

| 情况 | 结果 |
| --- | --- |
| 有效副本是 1（只有一台 block，或当时只写了一份），而这一份所在的节点丢了 | 这些对象读不出来，也不会自动出现在别的机器上 |
| 某个对象的全部数据副本都丢了 | 该对象不可读，没有修复流程把它补回来 |
| 索引的 primary 不可达 | 写路径会失败（包括 Put / Delete 等要更新 locator 的操作），避免脑裂。不是自动切主 |
| 新的索引节点加入 | 不会自动拉历史 key，不能靠加一台空节点立刻接过索引 |
| block 进程重启 | 优先读本地快照并补扫新数据，快照不可用则仍要全量扫描。这能缩短常见重启，但不是无状态的秒级替换，也没有测过确定上限 |
| 节点或磁盘彻底丢失 | 缺的数据副本不会迁移或重建；冗余度下降后一直缺着，直到人工处理（目前也还没有现成的修复工具链） |
| FUSE 尚未 `close` 的写入 | 只在客户端临时文件里，集群里还没有这个对象；挂载进程或 API 在关闭前退出，这部分内容不会进 block |
| 「任何情况下秒级恢复」或「一秒都不能停」的数据库负载 | 不是当前目标，也没有这样的测试或保证 |

## 用得省心

对使用者来说，省心就是：坏了不用自己管、写进去的东西不会悄悄少副本、加机器也不用手工搬数据。探测和避让只能让读在坏点上继续，还做不到这一点。要让人放心，系统需要自己把实际状态修回期望状态。

打算按这个顺序补：

1. **对象副本自动补齐**（第一期已落地，见下一节）：活着的 block 够用时，把不足的副本再写到别的节点。
2. **索引自愈**（还没有做）：dleveldb 主节点不可达时能安全切主；新索引节点能追上历史 key。
3. **block 更快恢复**（第一期已落地）：节点本地写 `recmap.s3m` 快照，重启时优先读快照并补扫新写入的部分；快照不可用则仍全量扫描。没有测过确定的启动时间。
4. **路径变瘦**（还没有做）：API 流式上传 / 下载，避免整个对象进内存；这也会让大文件的补齐和 FUSE 更稳。

这些都做完之前，不要宣传高可用，也不要说能扛「一秒都不能停」的数据库负载。

## 第一期：对象副本补齐

已经做的是一次「只增不删」的对账。API 会扫描可见的对象 key，比较「活着的数据副本数」和 `min(配置副本数, 当前存活的 block 节点数)`。不够就从一份还活着的副本读出内容，再 Put 到还没有这份对象的存活节点，并写上新的 locator。

- 手动触发：`POST /_s3dfs/repair`
- 后台周期：`S3DFS_REPAIR_INTERVAL_MS`，默认 30 秒；设为 0 则只保留手动触发
- 加机器、有效副本从 1 或 2 变成 3 时，已有对象也可以被补齐
- 某一副本所在节点宕机、但别处还有活副本、并且还有空闲的存活节点时，会再写一份

第一期明确不做、也不要默认认为已经有的：

- 没有活副本的对象（单副本丢掉，或全部数据节点都丢了）补不回来
- 不会删除指向 down 节点的旧 locator；节点带着原盘回来后，可能暂时多于配置的副本数
- 补齐仍走现有的整对象 Get / Put，大对象会进 API 内存，和现在的写入限制相同
- 不包含索引切主、索引追赶
- 控制台目前没有补齐按钮，只走管理接口或后台任务

## 还没有做的

- 退役失效 locator，以及把数据从 down 节点迁走
- dleveldb 节点加入后的范围迁移 / catch-up repair
- dleveldb primary 不可达时的安全写故障转移
- block 重启在快照不可用时仍可能全量扫盘；启动时间没有测过，不能写成秒级指标
- 针对掉点、切主、重启的恢复时间测试，因此文档里不写具体的秒数指标

有活副本时，现在不但能躲开坏点，还可以在还有空闲节点时把份数补回去。索引写故障转移如果缺着，只把副本补齐做完，仍然不能单独做到连续可用。

## 和设计方向的关系

要把「故障当作常态、尽量自己恢复」做成，需要把两件事分开：服务进程能否被替换，以及状态下沉的那一层是否自己扛得住。API 已经比较接近可替换；索引和 block 仍是有状态的。状态下沉到 dleveldb 和 `.blk` 之后，可靠性底线就在这两层：副本补齐是 block 这一侧的对账；索引切主和追赶还缺着。只把 API 做快，并不能单独做到连续可用。
