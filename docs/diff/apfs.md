# 与 APFS 的对照

| | |
| --- | --- |
| 日期 | 2026-11-21 |
| 读者 | 要从 Apple 文件系统里拿克隆、共享空间和元数据校验的人 |
| s3dfs | 以当时仓库的 [架构](../architecture.md)、[能力](../capabilities.md) 为准 |
| APFS | 以 Apple 的文件系统参考和安全指南为准。2016 年 Adam H. Leventhal 对校验和的说明与之一致 |
| 怎么读 | 标准对照的项目和 s3dfs 列，与本目录其他文件系统对照相同。特色只写 APFS 多出来的部分 |

APFS 是 Apple 平台上的本地文件系统，面向闪存。一个容器里多个卷共享剩余空间。元数据对象带校验和，用户数据块不校验。同卷克隆只改元数据，直到某一边被改写。s3dfs 的同集群 Copy 先共享已有记录，某一边被覆盖时再写新记录。

## 原理与细节

标准对照只对齐结论。这里写出结论从哪条原理来，以及能对上的字节、步数和规模。s3dfs 这一列在本目录各份对照里相同。

| 点 | s3dfs | APFS |
| --- | --- | --- |
| 分层 | 三种进程。dleveldb 只存 locator，block 里的 C 引擎只追加记录，API 不打开本地盘。对象变多，增加的是 KV 条数和少量大文件，不是一对象一文件 | 一个容器里有对象映射、空间管理器和多个卷。卷共享容器的剩余空间。元数据对象写时复制，用检查点提交。用户数据是 extent，不是第二条元数据 |
| 磁盘上的单位 | `blocks/` 下的文件名是 20 位块号加 `.blk`，默认 1 GiB。记录小端，魔数 `S3R1`（`0x31523353`）。帧依次是 magic u32、rec_len u32、tags、crc32 u32，再重复 rec_len u32 和 magic u32，开销 20 字节。标签依次是 type u16、length u32、value。不认识的标签跳过。`recmap.s3m` 魔数 `S3M1`，只是重启缓存；末尾 4 字节 CRC 对不上就重扫 `.blk` | 容器块常见 4 KiB。每个元数据对象有对象头。文件的物理位置记在文件 extent 记录里。克隆只增加新的 extent 引用，不立刻复制这些块 |
| 名字怎么找到字节 | 索引值是 JSON，`v` 为 3。第 0 份的键是 `bucket/key`，第 i 份（i≥1）是 `bucket/key:i`。里面有 `nodeId`、`address`、`recId`，没有文件偏移。`recId` 是标签 `0x000E` 的 u64。compact 可以改块号和偏移，不改 `recId` | 卷里的路径找到 inode，inode 的 extent 记录给出容器里的物理块。没有中心 KV。同卷克隆的两个文件在改写之前指着同一段物理块 |
| 一次写 | 默认 3 份，法定人数是多数：3 份里要 2 份。同一段字节写到不同 `@zone`。引擎把记录追加进当前 `.blk`，写缓冲默认 1 MiB，flush 默认 fsync。凑够 2 份才写索引；没凑够就删掉这次已写的 locator。放得进缓冲的对象默认 zstd，压不小则 `compressType=none`。超过 1 MiB 的原始 Put 按 1 MiB 交给 block，这种对象不压缩 | 元数据写出新对象，检查点把容器根换成新的对象映射。崩溃后回到上一个检查点。用户数据块按设备的写入完成，文件系统不给它们做第二份 |
| 一次读 | 先取 locator，跳过 down 的节点，按 `recId` 取记录。记录上的 CRC 是键字节接上正文。locator 里的 `crc` 是压缩前正文的 CRC-32。对不上就试下一份。链式对象用标签 `0x0006` 的 `PREV` 指向上一条 extent 的 `recId`，最后一段 kind 为 3 | 读 extent 指向的物理块。元数据对象用头里的 Fletcher-64 核对。用户数据块没有文件系统校验，读出来的就是设备返回的字节 |
| 校验放在哪 | 帧内 CRC-32 覆盖前 8 字节加全部标签，初值按 `crc32_update(0, …)` 计算，算法是 CRC-32/ISO-HDLC，反射多项式 `0xEDB88320`，与 zlib.crc32 相同。正文 CRC 另记在标签 `0x0004` 和 locator 里。kind：1 单条对象，2 中间 extent，3 最后一段，4 墓碑 | Fletcher-64 在元数据对象头里，不在用户数据块上，也不在父指针的数据地址里。用户数据的静默损坏要靠设备的 ECC 或上面的备份 |
| 副本是什么形状 | 三份是同一段逻辑字节的三份完整记录，不是条带，也不是纠删片。没有主副本。后写的 locator 覆盖先写的。删除先写 kind 4 的墓碑，避免扫描把已删对象救回来 | 没有跨设备的对象副本。克隆共享的是同一容器里的物理块，改一边才分配新块。加密按卷，用的是卷密钥，不是每个对象一把 |
| 规模 | 每个可见对象至少一条 locator，3 副本是 3 条键。`.blk` 的个数约等于字节数除以 1 GiB。单进程活记录停在 2^30−1。索引按 key 涨，不按块涨 | 对象映射随元数据对象涨。克隆不按文件大小再占一份空间，直到发生写时复制。容器满的是所有卷一起满 |

## 标准对照

| 项 | s3dfs | APFS |
| --- | --- | --- |
| 它解决什么 | 大量小对象的 S3。key 由调用方指定 | Mac、iPhone 上的系统卷和数据卷。本机拷贝要立刻共享空间 |
| 跑在哪 | 多台机器。API、dleveldb 索引、block 三种进程。故障域是 block 上的 `@zone` | 一台机器上的一个容器 |
| 元数据 | 每个对象一条 locator JSON（v:3），在 dleveldb。Get 先问索引 | 容器里的元数据对象。每个对象带 8 字节 Fletcher-64 |
| 正文 | 追加进约 1 GiB 的 `.blk`。记录是 `S3R1` TLV。locator 记节点和 `recId`，不记偏移 | 用户数据块。文件系统不给这些块做校验，靠盘上的 ECC |
| 名字 | `bucket/key`。第 i 份（i≥1）在 `bucket/key:i` | 卷里的路径 |
| 冗余 | 默认同一份对象 3 份，落在不同 zone | 文件系统不跨机器复制。冗余在盘上 |
| 写成功 | 3 份里 2 份 block 成功即写索引。第 3 份由修复补。任一条 locator 失败则删掉本次已写的 locator | 元数据写时复制。事务结束时写检查点，读者看到检查点之后的卷 |
| 读和校验 | 读一份活副本。记录 CRC 和 locator 上的正文 CRC 对不上就换下一份 | 读元数据时核对 Fletcher-64。用户数据对不上时，没有另一份对象副本可换 |
| 损坏之后 | 健康检查跳过 down 节点。`repair` 把不足的份数补到仍在线的节点，并去掉 down 的 locator。一份都不活记 `lost` | 元数据坏了会牵出这一卷。用户数据的静默损坏靠盘 |
| 崩溃恢复 | `.blk` 里只承认完整记录。索引按法定人数写入。`recmap.s3m` 只是重启缓存，坏了就重扫 `.blk` | 从最后一个检查点继续。写了一半的元数据事务不会成为新的卷状态 |
| 扩容 | 新 block 只接新写入。旧 locator 留在原节点 | 容器里的剩余空间给所有卷共用。不因为加了卷就把旧文件搬走 |
| 某一刻 | 版本清单在索引，正文在 block 的 `$ver/` | 快照按写时复制留住某一刻。macOS 11 起系统卷从快照启动 |
| 压缩与配额 | 默认 zstd，压不小则存原文。没有桶配额 | 不按对象做 zstd。空间账在容器，不按卷把盘划死 |
| 拷贝 | CopyObject 读出再写入 | 同卷克隆只更新元数据。两边之后的修改才分配新空间 |

## 修复与运维

成熟度只使用这五档：没有、手工、规则自动、闭环、产品。闭环指发现之后会处理，并再看结果。产品指边界和运行记录已经交给值班使用，不依赖读源码。档写在每格开头。

| 项 | s3dfs | APFS |
| --- | --- | --- |
| 自我修复 | 规则自动。活副本不足时，周期任务或 `POST /_s3dfs/repair` 再写一份，并去掉指向 down 节点的 locator。一份都不活就记 `lost`，健康检查失败，不编造正文。没有测过恢复时间上限 | 手工。文件系统检查和从快照回退由人发起。用户数据没有第二份，发现损坏也不能换一份副本 |
| 自运维 | 规则自动。探活、flush、compact、repair 按周期跑。巡检规则在副本不足、空洞过高或有未落盘字节时执行对应动作；配置了扩容命令且负载持续高时才扩容。换盘、搬走旧 locator、缩容和重启只记下来。`lost` 在 API 进程内存里，重启从 0 再计 | 手工。容器、卷和加密由人管。空间共享不会自己修复坏块 |
| AI 辅助检查 | 手工。规则先做维护。本机模型只把七个模块的数字写成中文结论，并留下能和上一轮比较的 HTML。模型不读对象正文，不删除，不重启，不缩容。关掉模型时规则简报还在。模型不决定修不修 | 没有。没有用模型读容器校验结果 |
| 静默损坏巡检 | 规则自动。Get 时核对记录 CRC 和 locator 里的正文 CRC，不对就换一份副本。没有把所有 `.blk` 再读一遍的 scrub | 规则自动。读元数据时核对 Fletcher-64。用户数据块没有文件系统巡检，静默损坏靠盘 |
| 告警与升级 | 手工。未恢复事件进巡检决定，简报写出要看的节点。没有接上外部值班系统，也没有自动升级 | 手工。系统升级和快照由人安排。没有存储自己的值班告警 |

## 文件系统放在一起

成熟度只使用这五档：没有、手工、规则自动、闭环、产品。闭环指发现之后会处理，并再看结果。产品指边界和运行记录已经交给值班使用，不依赖读源码。下面只比本目录里的单机文件系统。s3dfs 这一行在各篇里相同。NFS、SMB、Ceph、Longhorn、GFS、TFS、FastDFS 和 RustFS 不在这张表里，各自的档仍写在该篇里。

| 系统 | 自我修复 | 静默损坏巡检 | 自运维 | 告警与升级 | 停在哪 |
| --- | --- | --- | --- | --- | --- |
| s3dfs | 规则自动 | 规则自动 | 规则自动 | 手工 | 副本不够会再写一份，Get 时 CRC 不对就换一份。没有把所有 `.blk` 再读一遍并修好的闭环，告警也没有接上外部值班 |
| ZFS | 闭环 | 闭环 | 规则自动 | 规则自动 | 读到坏块当场修，scrub 把没人读的块也走一遍，结果留在池的错误计数里。池在一台机器上 |
| Btrfs | 规则自动 | 规则自动 | 手工 | 手工 | RAID 1/10 的 scrub 可以用另一份修。scrub 和 balance 要人安排。RAID 5/6 不能当唯一副本 |
| HAMMER2 | 规则自动 | 规则自动 | 手工 | 手工 | 读时用 CRC，从卷可以恢复这一卷。没有默认定时把整卷读完并修好 |
| APFS | 手工 | 规则自动 | 手工 | 手工 | 元数据核对 Fletcher-64。用户数据没有第二份，静默损坏靠盘 |
| NTFS | 规则自动 | 没有 | 手工 | 手工 | 在线修复和日志重放管元数据。用户数据没有端到端校验，也没有第二份副本 |
| FFS | 手工 | 没有 | 手工 | 手工 | fsck 由人发起。数据块没有端到端校验。GEOM 镜像不自动跨机器补一份 |

s3dfs 和 ZFS 的差距在闭环：ZFS 修完会留下计数，scrub 覆盖没人读过的块。s3dfs 与 Btrfs、HAMMER2 同在规则自动，还没有到 ZFS 那一档。APFS 的用户数据没有可以换上的第二份。NTFS 和 FFS 的用户数据没有端到端校验。这些文件系统都不提供跨 zone 的 S3。

s3dfs 现在停在规则自动。下面两档还没有。纠删、IAM、KMS、Object Lock 和站点复制不在这张差距表里。

| 还差的档 | 还缺什么 |
| --- | --- |
| 闭环 | 把所有 `.blk` 再读一遍，能修的当时修，修完留下计数。停一台 block 或一台索引之后，健康检查回到 200 要多久，还没有测过 |
| 产品 | 准备接流量的集群上还没有容量数字，也没有五步演练的部署笔记。告警没有接上外部值班，升级没有交给值班的步骤。本机 localhost 的通过不能当作唯一副本 |

## 省心与数据保护

这一节写值班的人和数据本身。修复与运维一节是修复做到哪一档。这里写人可以不碰什么、人仍然必须碰什么，以及写下去、读出来、删错、整机丢失和另一场地各保护到哪。

| 项 | s3dfs | APFS |
| --- | --- | --- |
| 值班可以不碰 | 一台 block 宕了，不用改客户端，也不用手工指定另一台。读会换活副本，新的 Put 不再选这台。周期 repair 把第 3 份补上，并去掉指向 down 节点的 locator。flush 和 compact 到了阈值自己跑。巡检先给四段简报，人看「值班下一步」，不必先从七个模块的原始数字里找 | 一个容器里的多个卷共用剩余空间，不用先把盘切成互不相通的分区。同卷克隆大目录只改元数据。系统卷可以从快照启动，本机改坏了可以退回那个快照 |
| 值班仍要碰 | 换盘，并把盘装回原来的 nodeId。确认 `lost` 里的对象是不是业务唯一的一份。在真正承接流量的集群上做演练。没配扩容命令时，加机器是人做的。旧对象不会自己搬到新 block。索引达不到法定人数，或三份正文都没了，没有按钮能把字节变出来 | 用户数据没有文件系统校验，静默损坏要靠磁盘更换和自己的备份。加密卷的密钥丢了，容器还在也读不出来。Time Machine 这一类备份要人打开 |
| 写下去 | 默认 3 个 zone 里至少 2 台 block 落盘，才把 locator 写入索引。第 3 份可以稍后补。这次的 locator 没有写齐，已经写下的会删掉，调用方看不到半份。索引还要达到 dleveldb 的法定人数 | 元数据按检查点提交，崩溃后不会停在半次目录修改上。用户数据块的完整靠设备，不靠文件系统的第二份 |
| 读出来 | Get 按 locator 找还活着的节点，核对大小和 CRC，不对就换下一份。Head 在节点暂时不可达时可以用索引里的 size、crc、mtime，那是没有把正文读出来核对 | 只在读元数据时核对 Fletcher-64。用户数据读出来不跟另一份副本比 |
| 删错和覆盖 | Delete 后索引里立刻看不见。盘上先留墓碑，compact 才收回空间。墓碑防止扫 `.blk` 时把已删对象救回来。覆盖是新的 locator。开了版本时，旧正文在同一组 block 的 `$ver/` 里，不是另一场地的备份 | 本地快照还在时，可以从快照里找回文件。快照删了，这次删除就没有系统内的副本 |
| 整机或整盘没了 | 丢一台、对象还有活副本时，读可以继续；还有空闲节点就再补一份。三份都在丢了的盘上，或当时只写成一份且那份没了，记为 `lost`，健康检查失败，字节补不回来。`lost` 重启后从 0 再计，盘上的丢失还在 | 容器在这台机器上。没有第二台机器上的卷可以接过来 |
| 另一场地 | 没有把对象自动送到另一套集群、另一机房或一块备份盘。3 副本是这一套集群里的三台 block | 没有把容器送到另一台机器的内置步骤。离开这台机器的副本是备份功能，要人开 |

## 特色

| 只在 APFS 里的做法 | 它怎么做 | s3dfs 现在 |
| --- | --- | --- |
| 容器共享剩余空间 | 多个卷只占自己写下的部分，剩下的空间还在容器里。不必先把盘划成互不相通的分区 | 每台 block 自己的 `.blk`。桶没有配额，也不共享一块剩余空间账 |
| 克隆 | 同卷拷贝先共享 extent。调用方改一边，才给那一边分配新块 | CopyObject 把字节读出来再写入。另一台 block 上是独立的一份 |
| 元数据和用户数据的校验分开 | 元数据对象有 Fletcher-64。用户数据块没有文件系统校验 | 记录 CRC 和 locator 上的正文 CRC 都做。不把用户数据的校验让给盘 |
| 按卷加密 | 系统卷和数据卷分开。预启动卷和恢复卷不加密 | 一把 AES256，只覆盖放得进 1 MiB 缓冲的对象 |
| 从快照启动 | 系统卷可以停在某一个快照上，本机改动落在另一层 | 没有「集群从某一个快照启动」 |

## 留下的

同池拷贝可以先共享底层块，调用方改一边再写新块。多个卷共享剩余空间，快照和加密按卷设，不必先把盘划死。元数据校验和用户数据校验是两件事：元数据坏了会牵出一大片，值得单独保护。

## 不照搬的部分

用户数据不靠 APFS 自己做端到端校验，s3dfs 继续在记录和 locator 里记 CRC。克隆和共享空间都在一台机器的容器里，不替换跨 zone 的副本。S3 Copy 仍读出再写入；同池共享块只留作以后的拷贝优化，不在上线八项里。
