FastDFS 用 tracker 告诉客户端去哪台 storage。tracker 不保存每个文件的索引。同组 storage 互为镜像。s3dfs 的索引保存每个对象的 locator，写入要凑够法定人数才对调用方成功。

## 原理与细节

标准对照只对齐结论。这里写出结论从哪条原理来，以及能对上的字节、步数和规模。s3dfs 这一列在本目录各份对照里相同。

| 点 | s3dfs | FastDFS |
| --- | --- | --- |
| 分层 | 三种进程。dleveldb 只存 locator，block 里的 C 引擎只追加记录，API 不打开本地盘。对象变多，增加的是 KV 条数和少量大文件，不是一对象一文件 | tracker 只知道组和组里的 storage。文件存在哪一台，写在返回给调用方的文件 id 里。同组 storage 互为镜像，组内容量等于最小的那块盘 |
| 磁盘上的单位 | `blocks/` 下的文件名是 20 位块号加 `.blk`，默认 1 GiB。记录小端，魔数 `S3R1`（`0x31523353`）。帧依次是 magic u32、rec_len u32、tags、crc32 u32，再重复 rec_len u32 和 magic u32，开销 20 字节。标签依次是 type u16、length u32、value。不认识的标签跳过。`recmap.s3m` 魔数 `S3M1`，只是重启缓存；末尾 4 字节 CRC 对不上就重扫 `.blk` | 正文是 storage 本地文件系统上的一个文件，不是打进公共大块的记录。同步不传文件字节的日志，binlog 只记时间、操作和文件名 |
| 名字怎么找到字节 | 索引值是 JSON，`v` 为 3。第 0 份的键是 `bucket/key`，第 i 份（i≥1）是 `bucket/key:i`。里面有 `nodeId`、`address`、`recId`，没有文件偏移。`recId` 是标签 `0x000E` 的 u64。compact 可以改块号和偏移，不改 `recId` | 文件 id 是组名、路径和一段 Base64。Base64 里有源 storage 的标识、创建时间、文件大小、CRC32 和随机数。没有中心索引可以把 key 换成位置 |
| 一次写 | 默认 3 份，法定人数是多数：3 份里要 2 份。同一段字节写到不同 `@zone`。引擎把记录追加进当前 `.blk`，写缓冲默认 1 MiB，flush 默认 fsync。凑够 2 份才写索引；没凑够就删掉这次已写的 locator。放得进缓冲的对象默认 zstd，压不小则 `compressType=none`。超过 1 MiB 的原始 Put 按 1 MiB 交给 block，这种对象不压缩 | tracker 选一台 storage。这台 fsync 之后就返回文件 id。源 binlog 用大写 C 或 D。同组其他机器按 binlog 来拉，副本操作改成小写，避免再推回去。每台对端一个 mark 文件，记下 binlog 索引和偏移 |
| 一次读 | 先取 locator，跳过 down 的节点，按 `recId` 取记录。记录上的 CRC 是键字节接上正文。locator 里的 `crc` 是压缩前正文的 CRC-32。对不上就试下一份。链式对象用标签 `0x0006` 的 `PREV` 指向上一条 extent 的 `recId`，最后一段 kind 为 3 | 用文件 id 找到组和源 storage。组内读已经同步到的副本。id 里的 CRC32 用来核对读到的字节 |
| 校验放在哪 | 帧内 CRC-32 覆盖前 8 字节加全部标签，初值按 `crc32_update(0, …)` 计算，算法是 CRC-32/ISO-HDLC，反射多项式 `0xEDB88320`，与 zlib.crc32 相同。正文 CRC 另记在标签 `0x0004` 和 locator 里。kind：1 单条对象，2 中间 extent，3 最后一段，4 墓碑 | CRC32 编进文件 id，不在 tracker 里再存一份。没有独立的校验块，也没有父指针。对不上时没有自动改到已同步副本并回写源盘的协议步骤 |
| 副本是什么形状 | 三份是同一段逻辑字节的三份完整记录，不是条带，也不是纠删片。没有主副本。后写的 locator 覆盖先写的。删除先写 kind 4 的墓碑，避免扫描把已删对象救回来 | 组内是整文件镜像，不是条带。返回成功时通常只有源盘上有这份字节。其他份是之后的 binlog 推送 |
| 规模 | 每个可见对象至少一条 locator，3 副本是 3 条键。`.blk` 的个数约等于字节数除以 1 GiB。单进程活记录停在 2^30−1。索引按 key 涨，不按块涨 | tracker 的内存不随文件数涨。storage 上的文件数随对象数涨，因为一文件一个本地文件。新 storage 先由一台源用单线程做全量，再转入增量 |

## 标准对照

| 项 | s3dfs | FastDFS |
| --- | --- | --- |
| 它解决什么 | 大量小对象的 S3。key 由调用方指定 | 图片和视频。上传后拿系统生成的文件 id |
| 跑在哪 | 多台机器。API、dleveldb 索引、block 三种进程。故障域是 block 上的 `@zone` | tracker 加 storage。tracker 可以多台，彼此不存文件索引 |
| 元数据 | 每个对象一条 locator JSON（v:3），在 dleveldb。Get 先问索引 | tracker 只知道有哪些组、组里有哪些 storage。文件在哪写在文件 id 里 |
| 正文 | 追加进约 1 GiB 的 `.blk`。记录是 `S3R1` TLV。locator 记节点和 `recId`，不记偏移 | 落在 storage 的本地文件上。同组其他机器稍后按 binlog 把文件推过去 |
| 名字 | `bucket/key`。第 i 份（i≥1）在 `bucket/key:i` | 组名加路径，再加 Base64。Base64 里有源 storage、创建时间、大小、CRC32 和随机数 |
| 冗余 | 默认同一份对象 3 份，落在不同 zone | 一个 group 里的 storage 互为镜像。组内容量按最小的那台算 |
| 写成功 | 3 份里 2 份 block 成功即写索引。第 3 份由修复补。任一条 locator 失败则删掉本次已写的 locator | tracker 选中的那一台落盘后就返回。同组其他机器之后才同步 |
| 读和校验 | 读一份活副本。记录 CRC 和 locator 上的正文 CRC 对不上就换下一份 | 按文件 id 找到组和源 storage。组内读已经同步过去的副本。id 里的 CRC32 用来核对 |
| 损坏之后 | 健康检查跳过 down 节点。`repair` 把不足的份数补到仍在线的节点，并去掉 down 的 locator。一份都不活记 `lost` | 源机器在同步完成前坏了，这一份就没有了。组内已同步的副本仍可读 |
| 崩溃恢复 | `.blk` 里只承认完整记录。索引按法定人数写入。`recmap.s3m` 只是重启缓存，坏了就重扫 `.blk` | 每台对端一个 mark 文件，记下 binlog 索引和偏移。断开后从这里续 |
| 扩容 | 新 block 只接新写入。旧 locator 留在原节点 | 新 storage 先做一次全量，再转入增量。全量由一台源用一个线程推 |
| 某一刻 | 版本清单在索引，正文在 block 的 `$ver/` | 没有版本。同步的是文件的出现和删除 |
| 压缩与配额 | 默认 zstd，压不小则存原文。没有桶配额 | 不在存储层做对象压缩。组的容量上限是组内最小盘 |
| 拷贝 | CopyObject 读出再写入 | 组内同步就是把文件推到同组机器。没有 S3 Copy |

## 修复与运维

成熟度只使用这五档：没有、手工、规则自动、闭环、产品。闭环指发现之后会处理，并再看结果。产品指边界和运行记录已经交给值班使用，不依赖读源码。档写在每格开头。

| 项 | s3dfs | FastDFS |
| --- | --- | --- |
| 自我修复 | 规则自动。活副本不足时，周期任务或 `POST /_s3dfs/repair` 再写一份，并去掉指向 down 节点的 locator。一份都不活就记 `lost`，健康检查失败，不编造正文。没有测过恢复时间上限 | 手工。binlog 把已经写到源盘上的文件推给同组。源盘在推完之前坏了，这一份不会被自动造出来 |
| 自运维 | 规则自动。探活、flush、compact、repair 按周期跑。巡检规则在副本不足、空洞过高或有未落盘字节时执行对应动作；配置了扩容命令且负载持续高时才扩容。换盘、搬走旧 locator、缩容和重启只记下来。`lost` 在 API 进程内存里，重启从 0 再计 | 手工。新 storage 的全量同步要人盯着，源忙时可能一直推不完。tracker 不替每个文件做修复 |
| AI 辅助检查 | 手工。规则先做维护。本机模型只把七个模块的数字写成中文结论，并留下能和上一轮比较的 HTML。模型不读对象正文，不删除，不重启，不缩容。关掉模型时规则简报还在。模型不决定修不修 | 没有。文件 id 里的 CRC32 不是模型检查 |
| 静默损坏巡检 | 规则自动。Get 时核对记录 CRC 和 locator 里的正文 CRC，不对就换一份副本。没有把所有 `.blk` 再读一遍的 scrub | 手工。文件 id 里带 CRC32，调用方或存储可以核对。没有定时把组内文件再读一遍的 scrub |
| 告警与升级 | 手工。未恢复事件进巡检决定，简报写出要看的节点。没有接上外部值班系统，也没有自动升级 | 手工。同步进度在 mark 文件里，要人看。没有自动升级 |

## 文件系统放在一起

成熟度只使用这五档：没有、手工、规则自动、闭环、产品。闭环指发现之后会处理，并再看结果。产品指边界和运行记录已经交给值班使用，不依赖读源码。下面只比本目录里的单机文件系统。s3dfs 这一行在各篇里相同。NFS、SMB、Ceph、Longhorn、GFS、TFS、FastDFS 和 RustFS 不在这张表里，各自的档仍写在该篇里。

| 系统 | 自我修复 | 静默损坏巡检 | 自运维 | 告警与升级 | 停在哪 |
| --- | --- | --- | --- | --- | --- |
| s3dfs | 规则自动 | 规则自动 | 规则自动 | 手工 | 副本不够会再写一份，Get 时 CRC 不对就换一份。没有把所有 `.blk` 再读一遍并修好的闭环，告警也没有接上外部值班 |
| ZFS | 闭环 | 闭环 | 规则自动 | 规则自动 | 读到坏块当场修，scrub 把没人读的块也走一遍，结果留在池的错误计数里。池在一台机器上 |
| Btrfs | 规则自动 | 规则自动 | 手工 | 手工 | RAID 1/10 的 scrub 可以用另一份修。scrub 和 balance 要人安排。RAID 5/6 不能当唯一副本 |
| HAMMER2 | 规则自动 | 规则自动 | 手工 | 手工 | 读时用 CRC，从卷可以恢复这一卷。没有默认定时把整卷读完并修好 |
| APFS | 手工 | 规则自动 | 手工 | 手工 | 元数据核对 Fletcher-64。用户数据没有第二份，静默损坏靠盘 |
| NTFS | 规则自动 | 没有 | 手工 | 手工 | 在线修复和日志重放管元数据。用户数据没有端到端校验，也没有第二份副本 |
| FFS | 手工 | 没有 | 手工 | 手工 | fsck 由人发起。数据块没有端到端校验。GEOM 镜像不自动跨机器补一份 |

s3dfs 和 ZFS 的差距在闭环：ZFS 修完会留下计数，scrub 覆盖没人读过的块。s3dfs 与 Btrfs、HAMMER2 同在规则自动，还没有到 ZFS 那一档。APFS 的用户数据没有可以换上的第二份。NTFS 和 FFS 的用户数据没有端到端校验。这些文件系统都不提供跨 zone 的 S3。

s3dfs 现在停在规则自动。下面两档还没有。纠删、IAM、KMS、Object Lock 和站点复制不在这张差距表里。

| 还差的档 | 还缺什么 |
| --- | --- |
| 闭环 | 把所有 `.blk` 再读一遍，能修的当时修，修完留下计数。停一台 block 或一台索引之后，健康检查回到 200 要多久，还没有测过 |
| 产品 | 准备接流量的集群上还没有容量数字，也没有五步演练的部署笔记。告警没有接上外部值班，升级没有交给值班的步骤。本机 localhost 的通过不能当作唯一副本 |

## 省心与数据保护

这一节写值班的人和数据本身。修复与运维一节是修复做到哪一档。这里写人可以不碰什么、人仍然必须碰什么，以及写下去、读出来、删错、整机丢失和另一场地各保护到哪。

| 项 | s3dfs | FastDFS |
| --- | --- | --- |
| 值班可以不碰 | 一台 block 宕了，不用改客户端，也不用手工指定另一台。读会换活副本，新的 Put 不再选这台。周期 repair 把第 3 份补上，并去掉指向 down 节点的 locator。flush 和 compact 到了阈值自己跑。巡检先给四段简报，人看「值班下一步」，不必先从七个模块的原始数字里找 | tracker 不随文件数量变大，不用为每张图扩 tracker 的内存。组内同步从 mark 文件里的偏移续传，断了不用人算出从哪个文件重新推 |
| 值班仍要碰 | 换盘，并把盘装回原来的 nodeId。确认 `lost` 里的对象是不是业务唯一的一份。在真正承接流量的集群上做演练。没配扩容命令时，加机器是人做的。旧对象不会自己搬到新 block。索引达不到法定人数，或三份正文都没了，没有按钮能把字节变出来 | 上传返回之后，不能假设同组其他机器已经有这份文件。源盘在 binlog 推完之前坏了，要业务重传，系统补不出字节。新机器的全量是单线程，源忙时要人看它是不是一直推不完。组里有一块小盘，加一块大盘也不会让这组变大 |
| 写下去 | 默认 3 个 zone 里至少 2 台 block 落盘，才把 locator 写入索引。第 3 份可以稍后补。这次的 locator 没有写齐，已经写下的会删掉，调用方看不到半份。索引还要达到 dleveldb 的法定人数 | 保护到源 storage 落盘为止。同组其他副本是返回之后的事。这个窗口里没有第二份 |
| 读出来 | Get 按 locator 找还活着的节点，核对大小和 CRC，不对就换下一份。Head 在节点暂时不可达时可以用索引里的 size、crc、mtime，那是没有把正文读出来核对 | 文件 id 里的 CRC32 能发现读到的字节不对。没有「自动改到另一台已经同步完的机器，并把源修回去」的步骤 |
| 删错和覆盖 | Delete 后索引里立刻看不见。盘上先留墓碑，compact 才收回空间。墓碑防止扫 `.blk` 时把已删对象救回来。覆盖是新的 locator。开了版本时，旧正文在同一组 block 的 `$ver/` 里，不是另一场地的备份 | 删除写入 binlog 再推。源上已经删了、副本还没收到时，副本上还能读到。没有回收站 |
| 整机或整盘没了 | 丢一台、对象还有活副本时，读可以继续；还有空闲节点就再补一份。三份都在丢了的盘上，或当时只写成一份且那份没了，记为 `lost`，健康检查失败，字节补不回来。`lost` 重启后从 0 再计，盘上的丢失还在 | 源机器丢了且还没推完的文件就没有了。已经推到组内其他机器的文件还在。组的容量和故障都按这一组算，不是按单独一个文件的 3 个 zone |
| 另一场地 | 没有把对象自动送到另一套集群、另一机房或一块备份盘。3 副本是这一套集群里的三台 block | 没有跨集群复制。一个组通常就在一边。另一场地要人再搭一套，并自己把文件推过去 |

## 特色

| 只在 FastDFS 里的做法 | 它怎么做 | s3dfs 现在 |
| --- | --- | --- |
| 单台落盘就返回 | 调用方拿到文件 id 时，往往只有源 storage 上有这份字节 | 2 份 block 成功才写索引。没凑够法定人数，调用方看不到成功 |
| binlog 只记名字 | 日志里是时间、操作类型和文件名，不记正文。源操作用大写（`C` 上传、`D` 删除），副本用小写，避免推回来 | 没有这条异步日志。复制发生在返回成功之前 |
| mark 文件 | 每个对端记下自己同步到的 binlog 索引和偏移，断线后续传 | 索引提交是一次法定人数写入，不靠偏移续传正文 |
| 组容量按最小盘 | 组里有一台盘小，整组的可用容量就是这一台 | 容量按各 block 自己的盘算。一份对象占 3 台的空间，不按组内最小盘截断 |
| 新机器单线程全量 | 源 storage 用一个线程把已有文件推给新机器。源很忙时，全量可能一直推不完 | 新 block 不接收旧对象。旧 locator 留在原节点，不先做全量 |

## 留下的

组是一种故障域：同一组里的机器互相备份，容量按最紧的那台算，这个账要单独记。文件 id 里带 CRC32，读的时候能核对，不必再问一个中心索引要校验值。tracker 不存每文件元数据，所以文件数量不决定 tracker 的内存。

## 不照搬的部分

上传返回时文件往往只在一台盘上。源 storage 在 binlog 推完之前坏了，这一份就没有了。s3dfs 的写成功仍是 3 份里的 2 份，不改成单台返回。S3 key 也不能换成 FastDFS 的文件 id。
