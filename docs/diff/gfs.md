# 与 GFS 的对照

| | |
| --- | --- |
| 日期 | 2026-11-21 |
| 读者 | 要从 Google 文件系统论文里挑机制、又不想换成那套架构的人 |
| s3dfs | 以当时仓库的 [架构](../architecture.md)、[能力](../capabilities.md) 为准 |
| GFS | 以 2003 年 SOSP 论文为准。后继系统是 Colossus，不在本文里 |
| 怎么读 | 标准对照的项目和 s3dfs 列，与本目录其他文件系统对照相同。特色只写 GFS 多出来的部分 |

GFS 给大文件的顺序读和末尾追加用。一个 master 记命名空间和 chunk 位置，chunkserver 存 64 MiB 的 chunk。s3dfs 给大量小对象用。两边都把元数据和正文拆开，对象大小和写成功条件不是一回事。

## 原理与细节

标准对照只对齐结论。这里写出结论从哪条原理来，以及能对上的字节、步数和规模。s3dfs 这一列在本目录各份对照里相同。

| 点 | s3dfs | GFS |
| --- | --- | --- |
| 分层 | 三种进程。dleveldb 只存数据位置，block 里的 C 引擎只追加记录，API 不打开本地盘。对象变多，增加的是 KV 条数和少量大文件，不是一对象一文件 | 一个 master 管命名空间，多台 chunkserver 存 chunk，客户端拿到位置后自己传字节。master 不转发文件内容。影子 master 只读 |
| 磁盘上的单位 | `blocks/` 下的文件名是 20 位块号加 `.blk`，默认 1 GiB。记录小端，魔数 `S3R1`（`0x31523353`）。帧依次是 magic u32、rec_len u32、tags、crc32 u32，再重复 rec_len u32 和 magic u32，开销 20 字节。标签依次是 type u16、length u32、value。不认识的标签跳过。`recmap.s3m` 魔数 `S3M1`，只是重启缓存；末尾 4 字节 CRC 对不上就重扫 `.blk` | 文件切成 64 MiB 的 chunk。chunk 内再按 64 KiB 做 32 位校验和，校验和与数据分开存放。chunk 身份是 64 位句柄，一旦分配就不变 |
| 名字怎么找到字节 | 索引值是 JSON，`v` 为 3。第 0 份的键是 `bucket/key`，第 i 份（i≥1）是 `bucket/key:i`。里面有 `nodeId`、`address`、`recId`，没有文件偏移。`recId` 是标签 `0x000E` 的 u64。compact 可以改块号和偏移，不改 `recId` | 路径在 master 的内存里映射到 chunk 句柄。句柄在哪些 chunkserver 上，由心跳报上来，不是唯一的持久记录。客户端缓存位置，直到租约或版本对不上 |
| 一次写 | 默认 3 份，法定人数是多数：3 份里要 2 份。同一段字节写到不同 `@zone`。引擎把记录追加进当前 `.blk`，写缓冲默认 1 MiB，flush 默认 fsync。凑够 2 份才写索引；没凑够就删掉这次已写的数据位置。放得进缓冲的对象默认 zstd，压不小则 `compressType=none`。超过 1 MiB 的原始 Put 按 1 MiB 交给 block，这种对象不压缩 | 客户端先向 master 要副本位置和主副本。数据沿副本链推进各台的缓冲区，再向主副本发写请求。主副本用租约定序，把顺序号传给从副本。每一份都应用成功，客户端才收到成功。租约大约 60 秒，靠心跳续 |
| 一次读 | 先取数据位置，跳过 down 的节点，按 `recId` 取记录。记录上的 CRC 是键字节接上正文。数据位置里的 `crc` 是压缩前正文的 CRC-32。对不上就试下一份。链式对象用标签 `0x0006` 的 `PREV` 指向上一条 extent 的 `recId`，最后一段 kind 为 3 | 用缓存的位置读一台 chunkserver。64 KiB 校验失败就向 master 要别的副本再读。record append 的填充可能对不齐，读者要跳过填充 |
| 校验放在哪 | 帧内 CRC-32 覆盖前 8 字节加全部标签，初值按 `crc32_update(0, …)` 计算，算法是 CRC-32/ISO-HDLC，反射多项式 `0xEDB88320`，与 zlib.crc32 相同。正文 CRC 另记在标签 `0x0004` 和数据位置里。kind：1 单条对象，2 中间 extent，3 最后一段，4 墓碑 | 校验和按 64 KiB 放在 chunk 旁边，不放在指向 chunk 的父指针里。chunk 版本号用来认出过期副本：主副本抬高版本后，版本旧的副本不再服务 |
| 副本是什么形状 | 三份是同一段逻辑字节的三份完整记录，不是条带，也不是纠删片。没有主副本。后写的数据位置覆盖先写的。删除先写 kind 4 的墓碑，避免扫描把已删对象救回来 | 默认 3 份完整 chunk。写路径上有主副本。三份内容在普通写里按同一顺序应用。record append 只保证至少一次，填充可以不同 |
| 规模 | 每个可见对象至少一条数据位置，3 副本是 3 条键。`.blk` 的个数约等于字节数除以 1 GiB。单进程活记录停在 2^30−1。索引按 key 涨，不按块涨 | 元数据按 chunk 涨，不按字节涨。64 MiB 一块，所以 master 内存里的条目远少于按小文件切的系统。论文把这一点当作 master 能放进内存的原因 |

## 标准对照

| 项 | s3dfs | GFS |
| --- | --- | --- |
| 它解决什么 | 大量小对象的 S3。key 由调用方指定 | 大文件的顺序读，以及在文件末尾追加 |
| 跑在哪 | 多台机器。API、dleveldb 索引、block 三种进程。故障域是 block 上的 `@zone` | 一个 master，多台 chunkserver。master 是命名空间的单点 |
| 元数据 | 每个对象一条数据位置 JSON（v:3），在 dleveldb。Get 先问索引 | master 内存里有命名空间和文件到 chunk 的映射。chunk 在哪些 chunkserver 上，由心跳报上来，master 不把位置当持久化的唯一来源 |
| 正文 | 追加进约 1 GiB 的 `.blk`。记录是 `S3R1` TLV。数据位置记节点和 `recId`，不记偏移 | 文件切成 64 MiB 的 chunk。chunk 里再按 64 KiB 做校验和 |
| 名字 | `bucket/key`。第 i 份（i≥1）在 `bucket/key:i` | 目录路径。文件切成编号的 chunk，名字本身不编码位置 |
| 冗余 | 默认同一份对象 3 份，落在不同 zone | 默认每个 chunk 3 份 |
| 写成功 | 3 份里 2 份 block 成功即写索引。第 3 份由修复补。任一条数据位置失败则删掉本次已写的数据位置 | 主副本定序。每一份都确认之后，客户端才收到成功 |
| 读和校验 | 读一份活副本。记录 CRC 和数据位置上的正文 CRC 对不上就换下一份 | 读一份副本。64 KiB 校验和失败就换另一份 |
| 损坏之后 | 健康检查跳过 down 节点。`repair` 把不足的份数补到仍在线的节点，并去掉 down 的数据位置。一份都不活记 `lost` | master 发现副本数下降后再复制一份 |
| 崩溃恢复 | `.blk` 里只承认完整记录。索引按法定人数写入。`recmap.s3m` 只是重启缓存，坏了就重扫 `.blk` | chunkserver 重启后用心跳把本机 chunk 报回 master。操作日志用来恢复 master 的命名空间 |
| 扩容 | 新 block 只接新写入。旧数据位置留在原节点 | 新 chunkserver 用心跳加入。已有 chunk 靠再复制和再平衡搬走 |
| 某一刻 | 版本清单在索引，正文在 block 的 `$ver/` | 论文里的快照靠 copy-on-write 把目录树留住。不是 S3 版本号 |
| 压缩与配额 | 默认 zstd，压不小则存原文。桶上可以设 `quotaBytes`，超过就拒绝这个桶的 Put | 论文不把压缩和配额当文件系统的一部分 |
| 拷贝 | CopyObject 读出再写入 | 按 chunk 复制。没有对象存储那种服务端 Copy |

## 修复与运维

| 项 | s3dfs | GFS |
| --- | --- | --- |
| 自我修复 | 活副本不足时，周期任务或 `POST /_s3dfs/repair` 再写一份，并去掉指向 down 节点的数据位置。一份都不活就记 `lost`，健康检查失败，不编造正文。没有测过恢复时间上限 | master 发现副本数下降后再复制一份。论文没有写修复完再读一遍确认，也没有恢复时间上限 |
| 自运维 | 探活、flush、compact、repair 按周期跑。巡检规则在副本不足、空洞过高或有未落盘字节时执行对应动作；配置了扩容命令且负载持续高时才扩容。换盘、搬走旧数据位置、缩容和重启只记下来。`lost` 写在 `$lost/`，重启后还在。未关闭的故障事件仍在进程内存里 | 心跳、再复制和再平衡写在论文里。换盘、扩容和 master 故障要人处理。没有交给值班的升级流程 |
| AI 辅助检查 | 规则先做维护。本机模型只把七个模块的数字写成中文结论，并留下能和上一轮比较的 HTML。模型不读对象正文，不删除，不重启，不缩容。关掉模型时规则简报还在。模型不决定修不修 | 2003 年的论文不用模型读集群状态 |
| 静默损坏巡检 | Get 时核对记录 CRC 和数据位置里的正文 CRC，不对就换一份副本。`scrub` 按数据位置重写坏副本并把检查数留在索引里，不把没有索引的 `.blk` 再读一遍 | 读时按 64 KiB 校验和核对，失败就换副本。没有把所有 chunk 再读一遍的独立巡检 |
| 告警与升级 | 未恢复事件进巡检决定，简报写出要看的节点。配置了 `S3DFS_ALERT_URL` 才把 `lost` 和布局不 ok 送出去。升级顺序写在部署文档里，不自动跳版本 | 客户端和 master 日志是当时的手段。没有产品化的告警和自动升级 |

## 省心与数据保护

这一节写值班的人和数据本身。修复与运维一节是修复做到哪一档。这里写人可以不碰什么、人仍然必须碰什么，以及写下去、读出来、删错、整机丢失和另一场地各保护到哪。

| 项 | s3dfs | GFS |
| --- | --- | --- |
| 值班可以不碰 | 一台 block 宕了，不用改客户端，也不用手工指定另一台。读会换活副本，新的 Put 不再选这台。周期 repair 把第 3 份补上，并去掉指向 down 节点的数据位置。flush 和 compact 到了阈值自己跑。巡检先给四段简报，人看「值班下一步」，不必先从七个模块的原始数字里找 | chunkserver 重启后用心跳把本机 chunk 报回来，不用人把位置表填回去。副本数下降后 master 再复制。读到坏的 64 KiB 校验和会换另一份，应用不用指定机器 |
| 值班仍要碰 | 换盘，并把盘装回原来的 nodeId。确认 `lost` 里的对象是不是业务唯一的一份。在真正承接流量的集群上做演练。没配扩容命令时，加机器是人做的。旧对象不会自己搬到新 block。索引达不到法定人数，或三份正文都没了，没有按钮能把字节变出来 | master 的操作日志和影子主要人部署，并演练日志丢了以后命名空间怎么回来。换盘后要确认 chunk 已经重新上报。再平衡会占网络，论文里没有一个让人不用看流量的开关 |
| 写下去 | 默认 3 个 zone 里至少 2 台 block 落盘，才把数据位置写入索引。第 3 份可以稍后补。这次的数据位置没有写齐，已经写下的会删掉，调用方看不到半份。索引还要达到 dleveldb 的法定人数 | 默认 3 份都确认才成功。主副本在租约里给写操作定序，两台不会把同一个 chunk 写成两个顺序。慢的那一份会拖住这次写 |
| 读出来 | Get 按数据位置找还活着的节点，核对大小和 CRC，不对就换下一份。Head 在节点暂时不可达时可以用索引里的 size、crc、mtime，那是没有把正文读出来核对 | 校验和按 64 KiB。record append 的填充在各副本上可能对不齐，读者要会跳过填充。这是客户端库的事，不是值班点一下 |
| 删错和覆盖 | Delete 后索引里立刻看不见。盘上先留墓碑，compact 才收回空间。墓碑防止扫 `.blk` 时把已删对象救回来。覆盖是新的数据位置。开了版本时，旧正文在同一组 block 的 `$ver/` 里，不是另一场地的备份 | 删除发生在 master 的命名空间里，chunk 上的空间稍后才回收。没有回收站。误删之后只能靠业务自己的副本 |
| 整机或整盘没了 | 丢一台、对象还有活副本时，读可以继续；还有空闲节点就再补一份。三份都在丢了的盘上，或当时只写成一份且那份没了，记为 `lost`，健康检查失败，字节补不回来。`lost` 写在 `$lost/`，重启后还在 | 丢一台 chunkserver，另外的副本还在就可以读，master 再复制一份。master 和它的日志一起没了，名字找不回来；chunk 里的字节还在盘上，位置可以靠心跳再报上来 |
| 另一场地 | 默认不把对象送到另一套集群。桶上打开复制并配置了地址之后，之后的 Put 和 Delete 才送出。3 副本仍是这一套集群里的三台 block | 论文里的快照是同一集群上的目录树，不会把 chunk 送到另一机房 |

## 特色

| 只在 GFS 里的做法 | 它怎么做 | s3dfs 现在 |
| --- | --- | --- |
| 主副本租约 | 一个 chunk 在租约期内只有一台主副本给写操作定序。租约过期后别人才能当主 | 三份对等。没有主副本，法定人数提交 |
| 位置不落成唯一事实 | chunk 在哪由 chunkserver 报上来。master 重启后靠心跳重建位置 | 数据位置是持久的。节点和 `recId` 写在索引里，不靠 block 心跳重建对象位置 |
| record append | 在文件末尾追加。各副本上的填充可能不完全对齐，读的时候靠校验和选一份能用的 | 对象按整段替换。覆盖是新的数据位置，不是在旧记录末尾追加 |
| 64 KiB 校验块 | 坏掉的是这一段，不必把整个 chunk 判废 | CRC 覆盖这一条记录里的键和正文。一条记录坏了就换整份对象副本 |
| master 不在数据路径上 | 客户端拿到 chunk 位置之后，字节直接和 chunkserver 来往 | 数据路径上是 API 和 block。索引只在取数据位置和提交数据位置时出现 |

## 留下的

元数据服务确认位置之后，不再站在每一次字节传输上。校验按比整段对象更小的单位做，读到坏数据就换副本。副本少了由控制面再复制，而不是等下次写入碰巧写满。

## 不照搬的部分

每个文件的元数据都放在一台 master 的内存里。对象数量上去之后，这台机器先满。写成功要等齐全部副本，比法定人数更严，一台 chunkserver 慢就会拖住写入。64 MiB chunk 和 record append 是为大文件末尾追加准备的，不替换 `.blk` 里的小对象记录。
## 总结

本篇用于确认元数据是否站在数据路径上。GFS 由中心节点分配位置，客户端随后直接访问数据节点；写成功要求每一份都确认。s3dfs 同样把索引限制在取位置和提交位置，正文在接口与数据节点之间传输。写成功维持多数：三份中的两份落盘即可。

对象名由调用方指定，因此每次读取仍查询索引。不把全部对象的元数据放进单一进程的内存，也不把大文件追加作为默认写入模型。

本篇不改变上线范围。跨机房的副本和恢复时间，以目标集群的演练记录为准。
