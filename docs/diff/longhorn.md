# 与 Longhorn 的对照

| | |
| --- | --- |
| 日期 | 2026-11-21 |
| 读者 | 要在 Kubernetes 里给 Pod 一块多副本的盘，同时又在看对象存储的人 |
| s3dfs | 以当时仓库的 [架构](../architecture.md)、[能力](../capabilities.md) 为准 |
| Longhorn | 以 Longhorn 文档里的卷、副本、引擎和备份为准。它是 Rancher 的容器块存储 |
| 怎么读 | 标准对照的项目和 s3dfs 列，与本目录其他文件系统对照相同。特色只写 Longhorn 多出来的部分 |

Longhorn 在 Kubernetes 里提供一块卷。默认把卷复制到多台节点，每份副本是该节点盘上的一条快照链。工作负载通过本机引擎访问这块卷，通常同时只有一个读写挂载。s3dfs 的对象可以放在多台 block 上被按 key 读取，没有「挂载一块盘」这一步。

## 原理与细节

标准对照只对齐结论。这里写出结论从哪条原理来，以及能对上的字节、步数和规模。s3dfs 这一列在本目录各份对照里相同。

| 点 | s3dfs | Longhorn |
| --- | --- | --- |
| 分层 | 三种进程。dleveldb 只存数据位置，block 里的 C 引擎只追加记录，API 不打开本地盘。对象变多，增加的是 KV 条数和少量大文件，不是一对象一文件 | 控制面在 Kubernetes 里。一块卷有一个引擎和多份副本进程。引擎对 Pod 呈现块设备，常见前端是 iSCSI。副本是节点本地盘上的文件，不是对象 |
| 磁盘上的单位 | `blocks/` 下的文件名是 20 位块号加 `.blk`，默认 1 GiB。记录小端，魔数 `S3R1`（`0x31523353`）。帧依次是 magic u32、rec_len u32、tags、crc32 u32，再重复 rec_len u32 和 magic u32，开销 20 字节。标签依次是 type u16、length u32、value。不认识的标签跳过。`recmap.s3m` 魔数 `S3M1`，只是重启缓存；末尾 4 字节 CRC 对不上就重扫 `.blk` | 每份副本一个目录。当前内容在 volume-head 镜像文件里，快照是这个头之前的差分文件。卷的大小是逻辑尺寸，空的部分不占满整个文件 |
| 名字怎么找到字节 | 索引值是 JSON，`v` 为 3。第 0 份的键是 `bucket/key`，第 i 份（i≥1）是 `bucket/key:i`。里面有 `nodeId`、`address`、`recId`，没有文件偏移。`recId` 是标签 `0x000E` 的 u64。compact 可以改块号和偏移，不改 `recId` | Pod 看见的是块偏移，不是 key。引擎知道副本在哪些节点。副本文件里的偏移就是卷的偏移。没有稳定记录号，也没有目录服务 |
| 一次写 | 默认 3 份，法定人数是多数：3 份里要 2 份。同一段字节写到不同 `@zone`。引擎把记录追加进当前 `.blk`，写缓冲默认 1 MiB，flush 默认 fsync。凑够 2 份才写索引；没凑够就删掉这次已写的数据位置。放得进缓冲的对象默认 zstd，压不小则 `compressType=none`。超过 1 MiB 的原始 Put 按 1 MiB 交给 block，这种对象不压缩 | 引擎把写发给各副本进程，副本把块写进自己的快照链顶层。副本数常见是 3，并且调度到不同节点。某份副本落后时，卷可以按配置处于降级并继续服务 |
| 一次读 | 先取数据位置，跳过 down 的节点，按 `recId` 取记录。记录上的 CRC 是键字节接上正文。数据位置里的 `crc` 是压缩前正文的 CRC-32。对不上就试下一份。链式对象用标签 `0x0006` 的 `PREV` 指向上一条 extent 的 `recId`，最后一段 kind 为 3 | 读也经过当前引擎，由引擎向副本要块。没有按对象 CRC 换一份的步骤。重建时把一份健康副本的链当成源，整份抄到新节点 |
| 校验放在哪 | 帧内 CRC-32 覆盖前 8 字节加全部标签，初值按 `crc32_update(0, …)` 计算，算法是 CRC-32/ISO-HDLC，反射多项式 `0xEDB88320`，与 zlib.crc32 相同。正文 CRC 另记在标签 `0x0004` 和数据位置里。kind：1 单条对象，2 中间 extent，3 最后一段，4 墓碑 | 没有独立的校验和树，也没有父指针校验。副本之间靠同步协议对齐。静默损坏要等读到坏块或重建失败才会暴露 |
| 副本是什么形状 | 三份是同一段逻辑字节的三份完整记录，不是条带，也不是纠删片。没有主副本。后写的数据位置覆盖先写的。删除先写 kind 4 的墓碑，避免扫描把已删对象救回来 | 每一份副本都是整卷的一份，不是条带。快照链是这一份副本内部的历史，不是另一台机器上的对象版本。备份把快照导出到 S3 或 NFS，那一步才离开这些节点盘 |
| 规模 | 每个可见对象至少一条数据位置，3 副本是 3 条键。`.blk` 的个数约等于字节数除以 1 GiB。单进程活记录停在 2^30−1。索引按 key 涨，不按块涨 | 控制面的对象是卷和副本，数量不随卷里的文件数涨。节点盘上的文件数随快照层数涨。卷越大，重建要拷的字节越多 |

## 标准对照

| 项 | s3dfs | Longhorn |
| --- | --- | --- |
| 它解决什么 | 大量小对象的 S3。key 由调用方指定 | Kubernetes 里的持久卷。调用方看见的是块设备 |
| 跑在哪 | 多台机器。API、dleveldb 索引、block 三种进程。故障域是 block 上的 `@zone` | 每个节点一个 Longhorn 组件。卷引擎在挂载这卷的节点上，副本进程在被选中的节点上 |
| 元数据 | 每个对象一条数据位置 JSON（v:3），在 dleveldb。Get 先问索引 | 卷的副本在哪、引擎在哪，由 Longhorn 的控制面记在 Kubernetes 里。没有每个文件一条索引 |
| 正文 | 追加进约 1 GiB 的 `.blk`。记录是 `S3R1` TLV。数据位置记节点和 `recId`，不记偏移 | 每个副本是节点盘上的快照文件链。卷的内容按块写进这条链 |
| 名字 | `bucket/key`。第 i 份（i≥1）在 `bucket/key:i` | 卷名。Pod 通过 PVC 使用它 |
| 冗余 | 默认同一份对象 3 份，落在不同 zone | 卷的副本数可配，常见是 3，并且尽量不落在同一节点 |
| 写成功 | 3 份里 2 份 block 成功即写索引。第 3 份由修复补。任一条数据位置失败则删掉本次已写的数据位置 | 引擎把写复制到各副本。副本数暂时不够时，卷可以按配置继续或停写，控制面会再建一份 |
| 读和校验 | 读一份活副本。记录 CRC 和数据位置上的正文 CRC 对不上就换下一份 | 读写都经过当前引擎。副本之间对不齐就重建，不按对象 CRC 换一份 |
| 损坏之后 | 健康检查跳过 down 节点。`repair` 把不足的份数补到仍在线的节点，并去掉 down 的数据位置。一份都不活记 `lost` | 一台节点没了，从仍健康的副本再建一份到别的节点。全部副本都坏时可以尝试 salvage，救不回就丢 |
| 崩溃恢复 | `.blk` 里只承认完整记录。索引按法定人数写入。`recmap.s3m` 只是重启缓存，坏了就重扫 `.blk` | 引擎和副本进程拉起来后续上卷。快照链里只认已经落盘的那一层 |
| 扩容 | 新 block 只接新写入。旧数据位置留在原节点 | 新节点可以接收重建出来的副本。已挂载的卷不会因为加了节点就自动拆开 |
| 某一刻 | 版本清单在索引，正文在 block 的 `$ver/` | 卷快照。备份把快照送到 S3 或 NFS，那是卷的备份，不是对象版本 |
| 压缩与配额 | 默认 zstd，压不小则存原文。桶上可以设 `quotaBytes`，超过就拒绝这个桶的 Put | 不做对象压缩。空间按卷的大小算 |
| 拷贝 | CopyObject 读出再写入 | 从备份或快照再做一卷。没有 S3 Copy |

## 修复与运维

| 项 | s3dfs | Longhorn |
| --- | --- | --- |
| 自我修复 | 活副本不足时，周期任务或 `POST /_s3dfs/repair` 再写一份，并去掉指向 down 节点的数据位置。一份都不活就记 `lost`，健康检查失败，不编造正文。没有测过恢复时间上限 | 副本进程失败后，控制器从健康副本把卷重建到别的节点，直到份数回到配置。全部副本都坏时 salvage 也救不回就仍是丢 |
| 自运维 | 探活、flush、compact、repair 按周期跑。巡检规则在副本不足、空洞过高或有未落盘字节时执行对应动作；配置了扩容命令且负载持续高时才扩容。换盘、搬走旧数据位置、缩容和重启只记下来。`lost` 写在 `$lost/`，重启后还在。未关闭的故障事件仍在进程内存里 | 控制器重建副本、把引擎重调度到节点上。备份计划、副本数和升级由人配置 |
| AI 辅助检查 | 规则先做维护。本机模型只把七个模块的数字写成中文结论，并留下能和上一轮比较的 HTML。模型不读对象正文，不删除，不重启，不缩容。关掉模型时规则简报还在。模型不决定修不修 | 卷和副本的状态是 Kubernetes 对象，不是模型结论 |
| 静默损坏巡检 | Get 时核对记录 CRC 和数据位置里的正文 CRC，不对就换一份副本。`scrub` 按数据位置重写坏副本并把检查数留在索引里，不把没有索引的 `.blk` 再读一遍 | 重建比较的是副本之间的内容。没有默认定时把卷上每个块再读一遍并核对校验和 |
| 告警与升级 | 未恢复事件进巡检决定，简报写出要看的节点。配置了 `S3DFS_ALERT_URL` 才把 `lost` 和布局不 ok 送出去。升级顺序写在部署文档里，不自动跳版本 | 卷故障会变成 Kubernetes 事件。没有独立的自动升级，也没有把模型结论交给值班 |

## 省心与数据保护

这一节写值班的人和数据本身。修复与运维一节是修复做到哪一档。这里写人可以不碰什么、人仍然必须碰什么，以及写下去、读出来、删错、整机丢失和另一场地各保护到哪。

| 项 | s3dfs | Longhorn |
| --- | --- | --- |
| 值班可以不碰 | 一台 block 宕了，不用改客户端，也不用手工指定另一台。读会换活副本，新的 Put 不再选这台。周期 repair 把第 3 份补上，并去掉指向 down 节点的数据位置。flush 和 compact 到了阈值自己跑。巡检先给四段简报，人看「值班下一步」，不必先从七个模块的原始数字里找 | 节点 NotReady 之后，卷的副本会在别的节点重建，Pod 不用改 PVC。副本数写在卷上，不用每次创建都重新决定 |
| 值班仍要碰 | 换盘，并把盘装回原来的 nodeId。确认 `lost` 里的对象是不是业务唯一的一份。在真正承接流量的集群上做演练。没配扩容命令时，加机器是人做的。旧对象不会自己搬到新 block。索引达不到法定人数，或三份正文都没了，没有按钮能把字节变出来 | 重建会读剩下的健康副本，磁盘和网络要人看，避免把最后一份也拖死。备份留几份、备份到哪，要人定。全部副本都坏时，salvage 要人判断还能不能用。Longhorn 自己的升级要人排 |
| 写下去 | 默认 3 个 zone 里至少 2 台 block 落盘，才把数据位置写入索引。第 3 份可以稍后补。这次的数据位置没有写齐，已经写下的会删掉，调用方看不到半份。索引还要达到 dleveldb 的法定人数 | 引擎把写送到各副本。副本暂时落后时，卷可以按配置在降级状态继续。这个窗口里份数是不够的，人要知道卷现在是不是降级 |
| 读出来 | Get 按数据位置找还活着的节点，核对大小和 CRC，不对就换下一份。Head 在节点暂时不可达时可以用索引里的 size、crc、mtime，那是没有把正文读出来核对 | 没有把卷上每个块再读一遍的校验。重建时把健康副本当作对的那一份 |
| 删错和覆盖 | Delete 后索引里立刻看不见。盘上先留墓碑，compact 才收回空间。墓碑防止扫 `.blk` 时把已删对象救回来。覆盖是新的数据位置。开了版本时，旧正文在同一组 block 的 `$ver/` 里，不是另一场地的备份 | 删掉 PVC 就会删卷，除非还留着备份。快照在同一组节点的盘上，这些节点都没了，快照也没了 |
| 整机或整盘没了 | 丢一台、对象还有活副本时，读可以继续；还有空闲节点就再补一份。三份都在丢了的盘上，或当时只写成一份且那份没了，记为 `lost`，健康检查失败，字节补不回来。`lost` 写在 `$lost/`，重启后还在 | 副本要调度到不同节点，才扛得住整机丢失。两份落在同一节点，这台没了就少两份 |
| 另一场地 | 默认不把对象送到另一套集群。桶上打开复制并配置了地址之后，之后的 Put 和 Delete 才送出。3 副本仍是这一套集群里的三台 block | 备份目标设成 S3 或 NFS，才有离开这组节点的一份。不设备份，副本只在这个 Kubernetes 集群的盘上 |

## 特色

| 只在 Longhorn 里的做法 | 它怎么做 | s3dfs 现在 |
| --- | --- | --- |
| 卷引擎 | 一块卷当前由一个引擎对 Pod 提供 iSCSI 或更新的块接口。读写都进这个引擎 | 没有卷引擎。API 按 key 找 block |
| 副本是快照链 | 节点上的一份副本由多层快照文件组成。新写入落在最新一层 | `.blk` 是追加的记录。快照不是副本的存放格式 |
| 重建副本 | 一份副本丢失后，从健康副本把卷抄到新节点，直到份数回到配置 | `repair` 按对象把缺少的那一份再写一份，不按整卷抄 |
| 备份目标 | 快照可以备份到 S3 或 NFS。恢复时从备份目标把卷做回来 | 自己就是对象存储。没有「再备到另一套 S3」 |
| 多节点读写 | 默认一块卷一个读写者。要多个 Pod 同时按文件写，前面还要再挂一层共享文件系统 | 多个客户端可以按不同 key 写。同一个 key 的并发是后写覆盖 |

## 留下的

副本少了就从还活着的那一份再做一份，并且新的一份要换一台机器。份数和故障域要写在卷的配置里，而不是等写入时临时决定。全部副本都没了，就要明确这卷找不回来。

## 不照搬的部分

s3dfs 不把对象卷成一块盘，也不用快照链当副本格式。修复的单位仍是对象，不是整卷重建。备份到外部 S3 不在这条路径上，因为调用方要存的就是这里的对象。
## 总结

本篇用于容器卷和对象副本的边界。Longhorn 以整卷和快照链为副本，副本不足时重建整卷。s3dfs 以对象为修复单位：活副本不足则再写一份，全部副本不可读则明确记为丢失，并在健康检查中可见。

不把快照链当作副本格式，也不把对象卷成供 Pod 挂载的磁盘。离开本集群的备份，靠桶上另行打开的复制，默认关闭。

Kubernetes 上的持久卷继续由卷系统负责。对象数据的唯一副本资格，仍以上线标准的目标集群演练为准。
