# 主流 S3 存储对照

对照日期：2026-11-20。这份文档回答一件事：若 s3dfs 要成为高可用、处处健壮、部署灵活、性能够用的对象存储，它该站在哪一类系统里，以及现在离这个标准还有多远。

和 RustFS 的逐项功能对照在 [rustfs.md](rustfs.md)。还没做完的实现缺口在 [todo.md](../todo.md)。本机吞吐只说明形状，数字在 [benchmarks.md](../benchmarks.md)，不拿来和任何一家的宣传图相减。

## 我们要成为什么样

高可用不是进程少，也不是默认改成纠删码。下面四件事要同时成立，少一件就不能把一套部署叫生产。

**写进去的份数和对外成功一致。** 配置了 3 副本时，对外成功表示已经有法定人数落在不同机器上，并且索引提交成功。只写成 1 份却返回 200，是把修复窗口暴露成静默少副本。3 份必须全部返回才成功，则一台慢节点就能让写入不可用，可用性比主流系统更差。目标是可配置的写法定人数：默认 3 副本、2 份成功即可对外成功，落后的那一份由修复补上；索引提交失败则这次写入对客户端失败。单机开发可以显式降到 1 副本，但 1 副本的布局不能叫高可用。

**读能换路，坏点会退出新写入，缺的份会补回来。** Get 在本次请求里试下一份副本。健康检查把节点标 down 之后，新的放置不再选它。活副本少于期望、并且还有空闲节点时，后台把份数补回去，并退役已经 down 的 locator。一份都不活，就记为丢失，不能报成修复成功。

**索引和正文各自有故障域。** 正文机器可以很多，索引保持一小簇（建议 3 台）。两边都要能在自身法定人数内继续服务。API 和控制台不保存对象正文，挂掉后换一台进程即可，前面用负载均衡把客户端接上去。索引主不可达时写入失败，这块还没有高可用。

**部署按角色，不按平台。** 单机是固定的三条进程：索引、block、API。生产是同一套角色加机器：索引 3 台，block 按容量加，API 按连接数加。压缩、副本数、块大小用环境变量改。不要求先建 CRUSH 规则、存储池和纠删 profile。机架或可用区以后要能写进放置规则；现在的哈希只在存活节点上转圈，还不知道机架。

灵活是这些旋钮都在同一条数据路径上，而不是为每种规模另写一套存储。性能的主场是大量小对象：正文打进大 `.blk`，组提交，按 `recId` 读，能压小就压。大对象走分段，不在 API 进程里攒下整个 body。本机 1 KiB、32 路并发、单副本约 3.1 万次写/秒，这是一台 MacBook Pro 上的 localhost 形状，不是上线承诺。

## 主流系统各自把高可用放在哪

下面只采用各项目公开文档里的架构事实。吞吐、耐久性的「几个 9」一律不摘进本文。

| | 它优化的负载 | 冗余 | 小对象怎么放 | 部署形态 | 一台数据机挂了 |
| --- | --- | --- | --- | --- | --- |
| [MinIO](https://minio.community/community/minio-object-store/operations/concepts/architecture.html) 社区文档（页面标注 AGPLv3） | 大对象、数据湖、横向扩盘 | 服务器池内 Reed-Solomon。纠删集 2–16 盘，初始化时定死。写至少要 K 个盘；半校验时写法定人数是 K+1 | 对象分片后按盘存。生产要求本地 JBOD，不要再套一层 RAID | 每台机器同一个 `minio server`。生产建议至少 4 台同构机器，前面加负载均衡。任何一台都能接请求并在内部转发 | 纠删集还够读/写法定人数就继续。healing 补片。扩容是追加新 pool，已有纠删集宽度不能改 |
| [Ceph RGW](https://ceph.io/en/news/blog/2025/rgw-deep-dive-1/) | 统一存储里的对象、块、文件 | 元数据池复制，数据池常用纠删（文档举例 4+2、8+3）。profile 建池后不能改 | 小对象会放大纠删的空间和恢复成本。文档建议小对象放复制池，大对象再进纠删池；桶索引必须在快盘上 | MON、MGR、OSD、RGW，再加池、CRUSH、PG。这是一套存储操作系统 | OSD 掉了由副本或剩余 K 片恢复。恢复要读剩余片再写新片，HDD 上会拖慢前台 |
| [SeaweedFS](https://github.com/SeaweedFS/seaweedfs) | 海量小文件，O(1) 次读盘 | 热数据按卷复制，写任何一份失败则整次失败。纠删在后台加到温数据上，写路径不付钱 | 追加进 volume。盘上约 40 字节/文件，内存里 16 字节索引，一次定位 | Master（常为 3 台 Raft）、Volume、Filer、可选的 S3 网关。`weed server -s3` 可以在一台机器上把它们拉起来 | Master 不在读路径上，客户端缓存卷位置。卷副本由复制和后台任务补 |
| [Garage](https://garagehq.deuxfleurs.fr/) | 机房之间、异构机器、自建 | 默认复制因子 3，尽量分到 3 个 zone。`consistent` 模式下读写法定人数保证读到自己的写；`degraded` 把读降到 1 份 | 元数据和数据目录分开，文档建议元数据放 SSD | 一个二进制。至少 3 台、每台一个公网可达地址。v2 用 `replication_factor` 和 `consistency_mode` | 复制因子 3 时，单 zone 故障仍可读写。写法定人数先返回，最后一份异步跟上，并用内存上限给客户端背压 |
| [RustFS](rustfs.md) | MinIO 一类的单进程数据面 | 纠删集，默认盘数上的 Reed-Solomon | 一对象（或一版本）一文件，小对象内联进 `xl.meta` | 一个进程同时提供 S3 和控制台 | 读、写都看纠删法定人数，缺片由 healing 补 |
| s3dfs 现在 | 大量小对象，索引和容量分开扩 | 默认 3 份整对象副本。多数成功就写索引，其余由修复补。`@zone` 先避开同一故障域 | 打进约 1GB 的 `.blk`，locator 只记节点和 `recId` | 索引、block、API、控制台分开起。单机三条进程，有效副本会降到 1。多台 API 无状态，步骤见 [deploy.md](../deploy.md) | 读改试剩余副本。修复会补份并退役 down 的 locator。索引主不可达时写入失败 |

## 对照之后留下的判断

**和 MinIO、RustFS、Ceph 的数据池比，s3dfs 不该把默认路径改成纠删码。** 那些系统用纠删换容量，适合大对象和盘数一次规划好的池。s3dfs 的主场是小对象：整份复制写起来直接，读一份就够，修复是再拷一份而不是集齐 K 片重算。纠删可以以后作为冷数据的另一种存储类，和 SeaweedFS 把纠删放在热写入之后的做法同类，不能替换 `.blk`。

**和 SeaweedFS 比，打包这个选择是对的，读路径还更重。** SeaweedFS 的 master 不在读路径上，卷位置由客户端缓存。s3dfs 每次 Get 都要先问索引要 locator，再问 block。索引必须小、必须快、必须自己有法定人数，否则小对象的延迟底数不在磁盘上，而在这一跳。block 侧已经是内存 `recId` 表加一次范围读，这和「一次定位」是同一类做法。

**和 Garage 比，写成功条件是多数。** 配置 3 副本时，2 份 block 写成功就提交索引，剩下那一份由修复补上。`S3DFS_WRITE_QUORUM` 可以改成更严。副本落在同一故障域时，份数看起来是 3，故障域只有 1；种子上的 `@zone` 会让放置先各取一个故障域。

**和 Ceph 比，元数据和正文分开是同一条原则，运维面不该跟着长。** Ceph 把桶索引放在复制的快盘上，把大对象放进纠删池。s3dfs 的 dleveldb 就是那块快的元数据，block 就是正文。差别是 Ceph 还要运营 MON、CRUSH 和 PG。s3dfs 的部署单位保持三种角色。单机开发允许 1 副本；生产清单里索引少于 3、block 少于副本数，就明确标成非高可用，而不是静默降级后仍用生产配置的名字。

**和这几家比，S3 的深度不是高可用本身。** IAM、KMS、站点复制、Object Lock、配额、审计决定能不能替换一套完整的对象平台。它们值得做，但排在写法定人数、索引可切换、入口无状态、请求可观测之后。没有这些，功能表再长也只是单点。

## 按这个标准，现在还缺什么

已经对齐的部分：默认 3 副本，达到多数即可对外成功，落后的份由修复补上；放置会先避开同一 `zone`；Get 会换副本；down 节点退出新的放置；修复会补份并退役失效 locator；没有活副本就记 `lost`；API 不在本地存正文；每个响应带 `x-amz-request-id`，`GET /_s3dfs/metrics` 给出状态码计数；块文件和组提交把小对象的 inode 问题拿掉了。部署步骤在 [deploy.md](../deploy.md)。

还没对齐的部分，按对高可用和性能的影响排：

1. 索引地址失败只能改连下一个 URL。新索引节点不会在这个仓库里追平历史 key，索引主不可达时写入失败。
2. 单次 Put 和分片完成仍在 API 进程里攒下整个对象。分片正文还在索引里，和「索引只放 locator」矛盾，也会把索引的磁盘和延迟拖出小对象的设计。
3. 多机上的小对象和大对象数字还没有。本机数字不能用来声称性能已经和主流系统同一档。

这些是实现顺序，不是另一份功能清单。做完以前，一套多机部署可以用于有人值守的小对象存储，不能当成已经具备主流系统那种写可用性和故障域隔离的生产集群。
