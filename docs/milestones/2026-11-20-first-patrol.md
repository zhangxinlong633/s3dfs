## 1. 自启

三个进程按仓库里的开发入口拉起。启动前 9000、9100、9800 都没有监听。LM Studio 已在 `127.0.0.1:1234` 提供 `google/gemma-4-26b-a4b`。

| 进程 | 命令 | 实际监听 |
| --- | --- | --- |
| 索引 | `pnpm dev:index` | `dleveldb index1 listening on 127.0.0.1:9800`，数据目录 `s3dfs/data/index` |
| block | `pnpm dev:block` | `s3dfs block block1 listening on 0.0.0.0:9100`，通告地址 `127.0.0.1:9100` |
| API | `bun src/main.ts`，副本 1，`S3DFS_STRICT_LAYOUT=0`，巡检凭证 `milestone` | Nest 监听 `:9000` |

本机这一次只有一台 block，没有设置 `@zone`。严格布局关闭，所以健康检查不会因为故障域为 0 而返回 503。生产部署仍按 [上线标准](../diff/production.md) 要求 3 个故障域。

## 2. 一次读写

`PUT /milestone/hello.txt` 返回 200。ETag 为 `"cdaa78b8"`，算法头是 `x-s3dfs-etag-algorithm: crc32`。

`GET` 读回的正文是：

```text
s3dfs 在 2026-11-20 从自启走到巡检。
```

随后 `GET /_s3dfs/health` 为 200：

```json
{"indexOk":true,"lost":0,"ok":true,"strict":false,"dataReplicas":1,"liveBlocks":1,"failureDomains":0,"reasons":[]}
```

## 3. 本机模型的结论

`pnpm patrol` 只跑一轮。进程 13.3 秒结束，退出码 0。规则没有执行修复、compact、flush 或扩容。结论由 Deep Agents 调用本机 Gemma 写成，并可由 `GET /_s3dfs/decisions` 取回。

模型原文：

> 巡检结论如下：
>
> 所有模块指标均正常，未发现越线情况。各模块检查结果记录如下：
> - **index**: 指标正常，延迟与副本匹配情况均在阈值内。
> - **block**: 坏块率及未刷盘数据均为 0，状态正常。
> - **layout**: 布局与存活块指标正常，故障域配置符合预期。
> - **repair**: 未发现丢失或短副本，修复状态正常。
> - **api**: 在途请求数与延迟均处于低位，运行平稳。
> - **scale**: 扩缩容趋势指标正常。
> - **care**: 未发现待处理任务，状态正常。

当时交给模型的数字是：

| 模块 | 指标 | 值 | 阈值 | 越线 |
| --- | --- | --- | --- | --- |
| 索引 | 可达 / 副本一致 / 写入延迟 / 对象数 | 1 / 1 / 0 ms / 1 | 1 / 1 / 200 ms / — | 否 |
| block | 空洞比例 / 未落盘字节 | 0 / 0 | 0.2 / 0 | 否 |
| 布局 | 成立 / 存活节点 / 故障域 | 1 / 1 / 0 | 1 / 1 / 1 | 否 |
| 修复 | 缺副本 / lost | 0 / 0 | 0 / 0 | 否 |
| API | 在途 / 延迟 p99 | 1 / 2 ms | 128 / 200 ms | 否 |
| 扩缩 | 连续超阈值 | 0 | 3 | 否 |
| 告警 | 未恢复事件 | 0 | 0 | 否 |

故障域的值是 0。模型把它写成「符合预期」。在这次单机、严格布局关闭的启动里，规则确实没有把它标成越线。三副本生产环境仍要求每个故障域分开配置。

## 4. 这一轮为了让结论落地而改的两处

| 位置 | 改动 |
