## 性能

正文是随机字节，每个对象一个新 key。服务端默认先试 zstd，压不小就存原文。1 KiB 预热 200 次、测量 2,000 次。1 MiB 预热 4 次、测量 40 次。32 并发预热 64 次、测量 2,000 次。带宽是逻辑 MiB/s，1 MiB = 1,048,576 字节。不要和本机 localhost 的 ops/s 相减。原始结果在 [性能记录](../benchmarks/2026-11-22.md)。

12:37 那轮只有 16 核那台打自己的接口：写 1 KiB 41.1 ops/s，读 1 KiB 58.6 ops/s。

12:56–13:02 三台各发起一轮，一轮结束再开始下一轮。两台有 API 的打自己的接口。没有 API 的那台走集群内网，打到 16 核那台的 API。16 核这轮写 1 KiB 是 40.2 ops/s，和上一轮同一档。

## 故障

测完时三台 block 和索引都已拉起。健康检查 200，`lost` 为 0。

| 步骤 | 结果 | 记录 |
| --- | --- | --- |
| 开始时三台 block 都在 | 通过 | 健康检查 200，`liveBlocks` 3，`lost` 0 |
| 停一台 block 后写入并读回 | 通过 | Put 200，Get 200。数据位置是 block1 和 block2，没有指向已停的那台 |
| 这台 block 回来后再修复 | 失败 | 数据位置仍是两份。修复报告扫到 87 个对象，`repaired` 为 0，没有给这个对象补上第 3 份 |
| 只留一台 block | 通过 | 新 Put 503。健康检查 503。原因是在线 block 只有 1 台、故障域只有 1 个，都少于配置的 3 |
| 两台 block 拉起 | 通过 | 健康检查回到 200 |
| 停一台索引 | 通过 | 写入 200。另一台 API 读到同一正文。索引回来之后仍能读到 |
| 索引回来后列举 | 失败 | 列举 200，`KeyCount` 为 0。对象当时能按 key 读到 |
| 三台 block 都停 | 通过 | 修复把扫到的 87 个对象记为丢失。健康检查 503，响应里的 `lost` 是 3 |
| 三台 block 拉起后再修复 | 通过 | 健康检查 200，`lost` 0，`liveBlocks` 3 |

修复和列举都只扫到第一台索引上的那一部分 key。按 key 读取会转到持有该 key 的索引，所以读得到。列表和自动补第 3 份没有覆盖到这次写入的对象。三台 block 都停时，修复报告里的丢失数是 87，健康检查响应里的 `lost` 是 3，两边扫到的 key 集合不一样。

同一天补上了原因。第一台索引启动时没有 peer，环上后来有了另外两台，它的扫描仍只读本机。改成环上不止一台就向其他索引要 key。改完后从第一台索引扫描 `fault/`，能看到 `gone.txt`、`index-down.txt`、`one-down.txt`。对桶 `fault` 的列举返回 `KeyCount` 3。
