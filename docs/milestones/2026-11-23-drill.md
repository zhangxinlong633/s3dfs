## 生产部署

晚上用指向这三台的环境文件 render 之后，在三台上执行了安装脚本。脚本把单元和每台的环境文件放到系统目录，执行了 `daemon-reload`，没有删除数据目录，也没有启动新的 `s3dfs-api@`、`s3dfs-index@`。正在服务的仍是原来的单元。装完后对外健康检查 200，`liveBlocks` 3，`lost` 0。新单元的环境文件指向现有的 block 和 index 目录。`/etc/s3dfs/secret.env` 原先不存在，脚本放入了示例，没有改正在使用的密钥文件。

## 晚上再跑的一轮

对象写法定人数的 drop-in 从 1 改成 2。索引的写法定人数 drop-in 仍是 1。16 核那台仍走分段路径。分段写入在布局不满足时直接回 503，不再先回 200。

| --- | --- | --- |
| 改完法定人数后三台都在 | 通过 | 健康检查 200，`liveBlocks` 3，`reasons` 空 |
| 只留一台 block | 通过 | 停掉没有 API 的那台 block，并停掉 8 核那台 API。健康检查 503，`liveBlocks` 1，故障域 1，`reasons` 两条。Put 503 |
| 拉起另外两台 | 通过 | 下一次健康检查 200，`liveBlocks` 3，`lost` 0 |

| 删演练桶 | 通过 | 索引按新的删除把非主分片上的残留清掉之后，列举从 3 个 key 变成 0。删桶 204。再列举 404 |
| 管理读 | 通过 | 没有身份时 `stats`、`cluster`、`buckets`、`metrics` 都是 401。健康检查 200 |
| 未关闭故障 | 通过 | 写入一条 id 为 `drill-care` 的未关闭事件，重启 16 核 API 后 `GET /_s3dfs/incidents/drill-care` 为 200，正文仍是这条。随后健康检查 200，`liveBlocks` 3，`lost` 0 |

加密分片按段封存、大于 1 MiB 的 `aws-chunked` 只留一块、以及超过 2 万条数据位置仍报真实条数，这三条在本机测试里通过。三台的 API 没有配置服务端加密密钥，所以加密分片没有在集群上再做一次。数据位置的全量计数没有在这三台上跑，避免再把 API 线程占住。
