# S3DFS 规模说明

| 口径 | 业务容量是用户能存下的字节。原始盘还要乘副本，并留出水印。数字来自当前代码的结构，不是目标集群上的实测 |
| 效力 | 不代替 [上线标准](diff/production.md)。没有目标集群的演练笔记时，本系统不保管业务数据的唯一副本 |
| 相关 | [部署](deploy.md)、[基准](benchmarks.md)、[架构](architecture.md) |

S3DFS 把对象正文打进大块文件，把定位信息放在可以单独扩容的索引里。按公开容量估算常用的平均对象大小 1 MiB、默认 3 副本、以及扩容水位 80% 来算，**100 EB 的业务容量对应 37.5 万台 1 PB 的 block，外加一套随 key 增长的索引**。100 台 500 TB 的磁盘是一个小得多的落地案例，见第 6 节。

## 1. 现在能承诺什么

可以接的，是另外还有一份副本、对象以小文件为主、并且按第 3 节的最小布局来摆的内部负载。

100 EB 是结构上算得通的目标，不是已经交付的集群。超过 1 MiB 的原始 Put 按块进入 block，API 大约留一块 1 MiB 缓冲；`aws-chunked` 仍整段读入。单对象默认上限仍是 1 GiB。纠删码、多用户 IAM、KMS、配额、站点复制和 Object Lock 还没有。2026-11-21 的巡检跑在一台机器、1 副本、严格布局关闭的三个进程上，只说明开发环境能从自启走到巡检。

## 2. 换算用的约定

下面每一节都用同一套约定，避免把原始盘和业务容量混在一起。

| 约定 | 取值 | 依据 |
| --- | --- | --- |
| 业务容量 | 用户写入的对象字节之和 | 副本和水位在此数之外另计 |
| 平均对象大小 | 1 MiB = 1,048,576 字节 | AWS 没有公布全球平均对象大小。公开的容量估算常用 1 MiB，对应「对象数量很多、少数对象很大」 |
| 副本 | 3 | `S3DFS_DATA_REPLICAS` 的默认值。3 份里 2 份成功即写索引，第 3 份由修复补齐。盘按 3 份买 |
| 水位 | 80% | `S3DFS_SCALE_HIGH_RATIO` 默认 0.80。用量到这一线就该加机器，规划时不把盘按 100% 卖出 |
| 1 PB、1 EB | 10^15 字节、10^18 字节 | 与磁盘标称的十进制一致 |
| 压缩 | 按压不小来买盘 | 默认 zstd。日志一类重复文本会变小；已经压缩或随机的内容记 `compressType=none`。容量按后者准备 |

一条能放进当前块的 1 MiB 记录，帧开销可以算死。帧头尾 20 字节，再加上 key、kind、`recId`、mtime、crc、压缩元数据和 value 的 tag。key 长 40 字节时，除 value 以外是 148 字节，占 1 MiB 的 0.014%。这个量不改变 37.5 万台这个万位。跨块对象的链会更长；单对象默认不超过 1 GiB，1 MiB 的平均值落在一条记录里。

## 3. 最小一套生产布局

接业务时从下面这套起。容量上去之后加 block，key 上去之后加索引。未配置 `S3DFS_SCALE_UP_CMD` 和 `S3DFS_SCALE_DOWN_CMD` 时，进程只做判断，不自己开关机器。

| 角色 | 起步 | 往上怎么加 |
| --- | --- | --- |
| 索引 | 3 台 | 只存 locator。节点随 key 增加。3 到 5 台是起步，不是封顶 |
| block | 3 台，三个 `@zone` | 正文在这里。严格布局开启时，存活节点或故障域少于副本数，新写入失败 |
| API | 至少 2 台，前面加负载均衡 | 无状态。TLS 在反向代理终止。台数跟并发走，不跟 EB 走 |
| 巡检 | 1 个进程，可后加 | 不在写入路径上。看模块状态，执行修复、compact、flush 和已配置的扩容 |

## 4. 一台 block 能放到哪里

每台 block 进程把本机全部活记录放进两张哈希表。表容量是 `uint32`，每次翻倍，并且必须是 2 的幂。容量到 2^31 时再翻倍会溢出，活记录数到达 2^30 就会触发这次失败的扩表。因此一台进程的活记录停在 **2^30 − 1 = 1,073,741,823 条**。`rec` 槽 40 字节，`key` 槽 24 字节，两张表在 2^31 个槽时合计 128 GiB，key 字符串另计。

按 1 MiB 的平均值，这 1,073,741,823 条的正文不到 1 PiB（2^50 字节）。一台标称 1 PB（10^15 字节）的盘，写满 1 MiB 对象时是 9.54 亿条，相当于这条上限的 89%。一台进程管得下这样一块盘，不必为了哈希表再把一块 1 PB 拆成两个进程。

## 5. 100 EB 业务容量

100 EB 指用户存进去的字节。换成机器要过四步。

1. 对象数 = 100 × 10^18 / 1,048,576 = **95.37 万亿**。一个对象在索引里有一条主键。
2. 三份副本的正文 = 300 EB。同一份字节写到三台 block 上。
3. 80% 水位以内才对外卖，磁盘 = 300 / 0.80 = **375 EB**。
4. 每台 block 按 1 PB 标称，block 台数 = 375 EB / 1 PB = **37.5 万台**。

| 项目 | 数 |
| --- | ---: |
| 业务容量 | 100 EB |
| 对象 | 95.37 万亿 |
| 副本正文 | 300 EB |
| 按 80% 水位准备的磁盘 | 375 EB |
| 1 PB 的 block | 375,000 台 |
| 每台活记录 | 9.54 亿，为单进程上限的 89% |
| 索引 locator | 286.1 万亿条 |

索引不在这 37.5 万台里面。默认写成功后，每个对象除主键外还有 `bucket/key:1` 和 `bucket/key:2`，所以 locator 是对象数的 3 倍。一条示例 locator 的 JSON 是 246 字节（节点名 `b000123`、地址 `10.0.0.12:9100`、1 MiB、`compressType=none`），配上 36 字节的 key，键和值本身约 **81 PB**。LevelDB 的索引块和写放大还在这 81 PB 之外。索引机的台数由这个体积和单机内存决定，节点可以继续加。

三台故障域要装得一样满。可用容量由最小的那一域决定，多出来的盘写不进新的三副本对象。原始 Put 在 API 里大约留 1 MiB；`aws-chunked` 仍会占住整段。100 EB 说的是落盘之后的容量。

先前如果把 100 EB 当成已经含副本的原始盘，只会得到 10 万台 1 PB 的 block，逻辑容量只有 33.3 EB。业务容量要按卖给用户的 100 EB 来买盘，所以是 37.5 万台。

## 6. 案例：100 台 500 TB

100 台、每台 500 TB（500 × 10^12 字节）是已经摆上的磁盘，合计 50 PB。它用来看一小簇怎么换算，不是第 5 节的上限。

按同一套约定，80% 水位以内的副本正文是 40 PB，业务容量是 40 / 3 = **13.333 PB**，对象 **127 亿**。若把盘从 0 写到 100%，业务容量可以到 16.667 PB、159 亿个对象；扩容判断在 80% 就会要求加机器，对外的数用 13.333 PB。

| 项目 | 80% 水位 | 盘写满 |
| --- | ---: | ---: |
| 副本正文 | 40 PB | 50 PB |
| 业务容量 | 13.333 PB | 16.667 PB |
| 对象 | 127 亿 | 159 亿 |
| 每台活记录 | 3.81 亿 | 4.77 亿 |
| 相对单进程上限 | 36% | 44% |

每台记录数都低于 2^30 − 1。索引放下这些对象的主键和两条副本 locator，靠增加索引节点。

这一簇的管理视图还不完整。集群对象数只取索引扫描的前 10 万条。每台 locator 数扫到 2 万条就停止，之后每台都记成 1。巡检快照超过约 8 KB 时从末尾丢掉 block 节点。100 台的磁盘字节仍可以逐台相加。37.5 万台的视图也受同样的限制。

## 7. 已经量到的读写形状

2026-11-17，一台 MacBook Pro 上的 localhost。N=3 是同一台机器上的三个 block 进程，没有多机网络。完整表格在 [基准](benchmarks.md)。这些数用来判断负载是不是小对象，不能当作 100 EB 的吞吐承诺。

| 用例 | 写 | 读 |
| --- | --- | --- |
| 1 KiB，N=3，串行，不压缩 | 2,785 ops/s，2.7 MiB/s | 4,151 ops/s，4.1 MiB/s |
| 1 KiB，N=3，32 路并发，不压缩 | 11,196 ops/s，10.9 MiB/s | 未单列 |

1 MiB、3 副本没有测量。多机网络上的 1 KiB 和 1 MiB 也没有。这次 N=3 测量时三台 block 都在，写的是三份；当前代码在多数副本成功后就写索引。小对象的 ops/s 主要由 HTTP 和索引决定。同一次测量里，100 B 和 1 KiB 的单副本写入几乎一样（6,985 与 6,937 ops/s）。

## 8. 故障时写入还在不在

严格布局保持开启时，存活 block 少于 3 台，或故障域不够，新的 Put 失败，`GET /_s3dfs/health` 返回 503。设计上停一台 block 后，3 份里 2 份成功仍可对外成功，修复再补第 3 份。这条路径有代码和测试，还没有准备上线的集群演练笔记。

没有任何活副本的对象记为 `lost`。这个计数和未关闭的故障事件在 API 进程内存里，重启后从 0 再计。没有测过恢复时间上限。

巡检可以执行修复、compact、flush，以及已经配置的扩容脚本。缩容、删除和重启只记下来。

## 9. 这些数什么时候可以改

在准备承接流量的机器和网络上测出 1 KiB 与 1 MiB、3 副本的读写，写入 [基准](benchmarks.md)，并按 [上线标准](diff/production.md) 做完目标集群演练、留下笔记。在那之前，第 3 节是起步布局，第 4 节和第 5 节是结构换算，第 6 节是 50 PB 磁盘的案例，第 7 节只说明一台笔记本上的形状。
