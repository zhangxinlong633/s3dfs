# 技术栈与代码体量

本文说明 s3dfs 为什么采用 TypeScript + C，以及为什么不必做成 RustFS 或 MinIO 那样的体量。行数按换行统计，统计日期为 2026-11-21（Asia/Shanghai）。跳过 `.git`、`target`、`node_modules`；开头 4 KiB 含空字节的文件视为二进制，不计入。s3dfs 与 dleveldb 另外跳过了 `dist`、`data`、`release`、`reports`、`coverage`。这不是性能对比，也不应用本文的行数去外推吞吐。

## 结论

s3dfs 要解决的问题更窄：对象正文整份多副本写入打包块，定位信息放在独立的 dleveldb 索引里，S3 API 只做入口，不参加存储环。没有纠删码条带、每对象 `xl.meta`、对称节点修复，也没有一次做全 IAM、站点复制和生命周期的完整企业面。

TypeScript 负责协议、控制和拼装，热路径和打包块用 C。现成库覆盖 HTTP、压缩、运行时这些底层，产品层只实现自己的模型。同一套控制面，用 TypeScript 写通常比 Go、Rust 或 C 更短：类型样板少，拼装和接口代码更密。异步尤其明显，一个 `async`/`await` 就能把等待索引、block 和磁盘的流程写成直线；换成 Go 的 goroutine 与通道、Rust 的 Future 与生命周期，或 C 的回调与状态机，同样的编排要写得更长，也更容易散落在多处。代码少，给人工和 AI 看的上下文就少，维护面也更小。省下的是工程和运行复杂度；磁盘会比纠删码多一些，因为默认是整份多副本。

## 同一套统计下的体量

数字来自本机工作树 `/Users/bruce/git/fss/rustfs`、`/Users/bruce/git/fss/minio`、`/Users/bruce/git/s3dfs` 和旁边的 `/Users/bruce/git/dleveldb`。MinIO 这份没有 `.git`，时间戳在 2026 年 2 月 13 日，与当时已停止维护的社区仓库是同一套，行数比 GitHub master（`7aac2a2`）略少。s3dfs 含当时工作区里的本地文件（例如 C 网关），不代表都已提交。

| 仓库 | 语言源码 | 说明 |
| --- | --- | --- |
| RustFS | Rust 约 179 万行（1932 个文件，不含测试目录）；含测试约 209 万行 | 自研 workspace crate 为主，第三方 `vendor` 很少 |
| MinIO（社区版） | Go 约 34 万行（877 个文件）；去掉 `*_test.go` 和 `*_gen.go` 后约 20 万行 | 核心几乎都在一个 `cmd` 包，再加 `internal` |
| s3dfs | TypeScript / JavaScript 约 2.0 万行，C/C++ 约 1.3 万行；二者合计约 3.3 万行 | 另有文档、锁文件和 JSON，整树文本约 4.8 万行 |
| dleveldb | TypeScript / JavaScript 约 0.6 万行 | 独立索引仓库，不计入上一行 |

按「正式源码」比，s3dfs 加 dleveldb 大约是 MinIO 的五分之一到六分之一，是 RustFS 的五十分之一量级。行数少，首先是因为模型窄，其次是现成库多，再就是 TypeScript 写控制面本身更短。若把现在的 API、索引客户端和控制逻辑换成 Go 或 Rust，同样的行为通常要写得更长；若整段改用 C，会再长一截。

s3dfs 当时工作树里，较大的几块是：`apps/api` 约 0.7 万行 TypeScript，`apps/s3-gateway` 约 0.6 万行 C，`packages/engine` 约 0.6 万行（C 引擎与绑定），`packages/control` 约 0.4 万行 TypeScript，`apps/fuse` 约 0.4 万行 C。控制台和文档也占一部分，但不在写入热路径上。

## 功能面不一样，不能只比行数

RustFS 走的是 MinIO 那条完整对象存储路线：纠删码、磁盘布局、S3、IAM、修复扫描、生命周期、站点复制、管理接口。这些每一层都要自己铺开，所以体量会到几十万乃至上百万行。它比 MinIO 再膨胀出 6 到 8 倍，主要不是功能突然多了那么多，而是用 Rust 几乎整栈重写，模块拆得很碎，还要兼容既有格式和管理面。

MinIO 更「健康」，是因为同样覆盖完整对象存储，正式源码大约 20 万行，结构集中，依赖走 `go.mod`。这更接近「把该做的功能做完」的体量。社区仓库本身已经停止维护，转向 AIStor；健康指的是代码形态，不是项目还在公开演进。MinIO 是 AGPL，思路可以看，实现不能搬进 s3dfs。RustFS 同样不要复制源码。

FastDFS 常被提到约十几万行 C。它主要是自研的私有协议和存储，并不覆盖完整 S3、IAM 这些表面，所以不能按行数判断已经比 s3dfs 功能更多。早期 MinIO 也更瘦，但现在能直接对照的，是已经长成完整对象存储的公开代码；能借鉴的是思路和边界，能直接搬的实现很少。

s3dfs 代码更少，不是因为这些系统的功能都已经做齐。尚未提供的能力（纠删码、站点复制、Object Lock、多用户 IAM、KMS 等）见 [待办](todo.md) 和 [能力](capabilities.md)。以后要加，也按「索引 + 打包块 + 整份副本」自己实现，不必把 RustFS 或 MinIO 的磁盘格式和模块切分搬过来。

## 依赖决定哪些必须自己写

公开能直接当成产品骨架的对象存储抽象很少。这里要分开看：控制面和数据面不是同一回事。控制面上，TypeScript 更相信第三方，HTTP、鉴权中间件、配置和编排都可以交给成熟的 package；Go、Rust、C 对外部依赖更谨慎，同样的控制逻辑更容易写进自己的仓库。数据面没有这种偷巧的余地，落盘格式、打包块、副本放置、修复和校验，各语言都得靠自己的实现，比的是模型和功力，不是谁的包更多。

TypeScript / Node 这一侧，HTTP、JSON、压缩、进程与包管理都有现成库，而且语言本身写协议、状态机和拼装更短，控制面可以少写很多。这不只是语法，也是编码习惯：默认先找 package，装进 `node_modules`，业务代码只写自己的逻辑。包用的人多，就更成熟、文档更全，控制面能直接借的面也更宽。Go 和 Rust 同样有模块和 crate，但系统软件里仍更常把协议、修复、存储布局写在自己的仓库里；C 更是长期以自研库为主，没有养成这种大规模复用的习惯。C 在 s3dfs 里只放引擎、打包块和需要抠性能的网关路径，避免从零铺一整套协议栈，也避免用更啰嗦的语言去写本可以由 TypeScript 收住的控制面。RustFS 这类实现里，第三方库多半只覆盖 HTTP、编码、压缩这些底层，产品层几乎没有现成骨架，只好自己造一堆 crate。MinIO 用 Go 标准库和模块依赖收住了不少底层，所以正式源码能停在约 20 万行。s3dfs 把产品模型再收窄一档，控制面按 TypeScript 的习惯尽量用包，数据面自己做打包块和引擎，源码才能停在数万行。

## 对维护和 AI 协助的影响

更多代码意味着更大的阅读面：改一处要带上的上下文更多，编译、测试、排障的路径更长，人工和模型消耗的 token 也更多。RustFS 那种上百万行、几十个自研 crate 的结构，单次改动很难完整放进上下文；MinIO 的单包 `cmd` 虽然集中，二十万行也已经不是能一口看完的面。s3dfs 把热路径收在少数 C 文件和 TypeScript 控制面里，模型和人都更容易一次看清写入、定位和修复。

TypeScript 改协议和拼装快，也方便 AI 做局部修改；C 负责落盘、拷贝和热路径，边界清楚，生成代码时也不容易把整栈铺开。这个组合适合现在的工作方式，前提是模型保持窄。若为了「完整对象存储」把纠删码、对称布局和全套 IAM 一次性铺上，行数和维护成本会重新靠向 MinIO，甚至在重写过程中靠向 RustFS。

省成本首先来自更简单的模型，同时 TypeScript 把控制面写短、C 只守热路径，也直接减少了要维护和送进模型的代码。磁盘上的空间换成了工程时间：多副本比纠删码占更多盘，但实现、修复和排机器都更直接。对小文件和低延迟写入，这个交换通常划算。

## 公开数据与据此推断的代码量

下面先列出能核对的公开数据，再据此推断这种做法大约能省下多少第一方代码。推断是量级判断，不是另一轮实测，也不能外推吞吐。

### 公开数据

[QSM Function Point Languages Table 5.0](https://qsm.com/resources/function-point-languages-table) 基于 2192 个已完成、且为单一语言的功能点项目，统计的是实现一个功能点所需的逻辑源码行。JavaScript 平均 47 行（中位数 53，范围 31 到 63），C 平均 97 行（中位数 99，范围 39 到 333），C++ 平均 50 行，Java 平均 53 行，C# 平均 54 行。表中没有 TypeScript、Go 和 Rust。QSM 建议缺项时用相近语言的系数，并加大不确定度。

Ardito 等人 2021 年在 [PeerJ Computer Science](https://pmc.ncbi.nlm.nih.gov/articles/PMC7959618/) 上比较了同一组 9 个算法在多种语言中的实现（来自 Energy-Languages 仓库）。平均每个源文件的 SLOC：C 为 209，C++ 为 186，Rust 为 144，JavaScript 为 107，TypeScript 为 95。这是小型算法内核，不是带框架的控制系统，只能看作语言密度的旁证。

[Google Open Source Insights（deps.dev）](https://deps.dev/) 在 2026 年 11 月 21 日（Asia/Shanghai）抓取时，登记的包数量大约是：npm 462 万，Go modules 248 万，Cargo crates 38.4 万。包的个数不等于质量，但能说明 JavaScript / TypeScript 可供直接依赖的面最大。

[GitHub Octoverse 2020](https://octoverse.github.com/2020/) 及其 [安全报告](https://octoverse.github.com/2020/static/github-octoverse-2020-security-report.pdf) 写到：在现代软件中，大多数应用 80% 或更多的代码来自依赖。该报告统计了活跃且启用依赖图的仓库（约 2019 年 10 月到 2020 年 9 月）：引用开源依赖最频繁的是 JavaScript（94%），其次是 Ruby 和 .NET（均为 90%）。直接依赖的中位数，JavaScript 为 10 个。在有 lockfile、因而能看到传递依赖的仓库里，JavaScript 的传递依赖中位数是 683 个，其后是 PHP 70、Ruby 68、Python 19。这组数字常被用来讨论供应链风险，这里只用来说明 TypeScript 控制面「把大量代码留在包里」是普遍做法。

### 据此推断

先把语言密度和「做了多少产品面」分开。QSM 表里没有 Go。若把 Go 近似成表中的 Java 或 C#（53 到 54 行/功能点）再和 JavaScript（47）比，语言密度只差大约一两成，解释不了 MinIO 约 20 万行正式源码和 s3dfs 加 dleveldb 约 4 万行之间将近 5 倍的差距。因此，省下的大头是模型更窄，没有一次铺开完整对象存储的纠删码、IAM、站点复制和管理面，而不是 TypeScript 比 Go 短那么多。RustFS 约 179 万行同样不能当成「若不用 TypeScript 就会变成这么多」；那是整栈重写后的膨胀。

控制面复用第三方，是第二层，也更难折成精确行数。按 Octoverse 的表述，跑起来的代码里大部分往往不在自己的仓库里。s3dfs 加 dleveldb 大约 2.6 万行 TypeScript，统计的是自己的协议、放置和拼装；HTTP、框架、压缩这些在 `node_modules` 里，不计入上一节的第一方行数。若改成 C 或系统软件里常见的习惯，较少依赖包、把这些写进自己的仓库，控制面第一方代码可能会数倍于现在。没有「把现成框架整段改写成第一方」的对照实验，所以这里只说方向和量级，不写死一个倍数。依赖变多，供应链面也会变大，这是同一组公开数据里并行存在的代价。

语言密度只作用在控制面，幅度更小。按 QSM 的平均值，同样功能点下 C 大约是 JavaScript 的 2.1 倍（97 除以 47）。把 TypeScript 近似为 JavaScript，当前约 2.6 万行控制面若改写成 C，大约会落到 5 到 6 万行这个量级。Ardito 那组小算法里，C 相对 TypeScript 约 2.2 倍，Rust 约 1.5 倍，方向一致，但样本小，不能单独当系数。数据面已经是 C，约 1.3 万行不会因为换语言再缩短。把这两块加起来，同样的窄模型若控制面也用 C 来写，第一方合计大约是 6.5 到 7 万行，对比现在约 4 万行，语言这一项大约省 2 到 3 万行。这是按逻辑行系数去折物理换行的量级，不是精确预测。

合在一起看：做现在这个窄模型，控制面用 TypeScript 和包、数据面用 C，第一方大约是已经数过的 4 万行。若控制面改成 C，仅语言密度就会多出大约 2 到 3 万行；若再几乎不用第三方、把协议栈写进仓库，控制面还会继续涨，但缺少对照，不宜再写成一个精确上限。若把产品面做成 MinIO 那样完整，即使继续用 TypeScript 加 C，第一方也很可能涨到十万行以上，因为数据面、S3 语义、修复和复制仍然要自己做。语言和包能缩短控制面，省不掉数据面。
