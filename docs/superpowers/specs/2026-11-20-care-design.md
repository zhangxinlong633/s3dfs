# 上线之后省心

日期：2026-11-20。

| | |
| --- | --- |
| 目标 | s3dfs 要成为最让人省心的系统。上线之后的问题先自我修复；修复不了就告诉用户发生了什么、已经试过什么、怎么找人，并给出一份 AI 可以直接接着做的说明 |
| 读者 | 实现和验收这条闭环的人 |
| 第一期 | 使用已经存在的副本修复、索引追平和扩缩容。不新发明修复动作，不自动重启进程 |
| 相关 | [故障与恢复](../../design-recovery.md)、[自动扩缩容](2026-11-20-autoscaling-design.md) |

## 1. 何时告警

每个修复周期结束之后判断一次。这个周期里已经跑过现有的副本修复。索引追平仍由 dleveldb 完成。扩缩容仍由评估器调用脚本。

下列任一成立，生成一条故障事件：

| 条件 | 含义 |
| --- | --- |
| 健康检查会返回 503 | 索引不可达、严格布局不成立，或本进程 `lost` 大于 0 |
| 本次修复记下 `lost` | 有对象已经没有任何活副本 |
| 缩容停在 `draining` | 过了该角色的冷却时间，数据仍迁不走 |

事件按「原因 + 涉及的桶或节点」去重。同一种事件在恢复前只发送一次。状态恢复之后再发送一条已恢复。恢复前不重复发送。

没有 `S3DFS_ALERT_URL` 时，事件只写入进程日志，不当成已经通知用户。

## 2. 发给谁

| 范围 | 去向 |
| --- | --- |
| 集群故障 | `POST S3DFS_ALERT_URL` |
| 能对应到具体桶 | 同一份说明再发到该桶已配置的 webhook |
| 找人 | 正文带上 `S3DFS_SUPPORT_CONTACT`，以及这次事件的详情地址 |

详情地址是 `{S3DFS_PUBLIC_API_URL}/_s3dfs/incidents/<id>`。未设置公开地址时，用 `S3DFS_ADVERTISE_ADDR` 拼出 API 地址。`GET /_s3dfs/incidents/<id>` 返回给 AI 的那份 JSON。

发送失败只记日志，事件保留。下个周期对同一条未送达的事件再试，不把它记成新故障。

## 3. 两份内容

给人看的正文使用普通文字，包含：

- 发生了什么
- 影响的桶或节点
- 已经自动做过什么
- 现在为什么还没有好
- `S3DFS_SUPPORT_CONTACT` 里写的找人方式
- 详情地址

给 AI 的 JSON 至少包含这些字段：

| 字段 | 内容 |
| --- | --- |
| `id` | 事件编号 |
| `time` | 发生时间 |
| `severity` | `action_needed` 或 `recovered` |
| `symptom` | 健康检查、`lost` 或 `draining` 的事实 |
| `tried` | 已经执行的修复和结果 |
| `doNot` | 不该再做的事。没有活副本的对象不能靠再跑修复补回来 |
| `next` | 建议的下一步：看健康检查、看 locator、看索引节点、以及必须由人做的操作 |
| `docs` | 相关文档路径 |
| `contact` | `S3DFS_SUPPORT_CONTACT` |
| `url` | 详情地址 |

## 4. 测试

不发送真实 HTTP。

| 用例 | 期望 |
| --- | --- |
| 修复后健康检查仍会 503 | 生成一条事件，告警地址收到一次 |
| 同一原因再次出现且未恢复 | 不再发送 |
| 状态恢复 | 发送一条 `recovered` |
| 事件能对应到桶，且该桶有 webhook | webhook 收到同一份说明 |
| 没有告警地址 | 不发送。事件保存在进程内，并写一条日志 |
| 对象 `lost` | JSON 的 `doNot` 写明不能靠修复补回 |
| 告警发送失败 | 事件仍在，下个周期可以再试 |
